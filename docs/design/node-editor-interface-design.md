# OmniLang 节点编辑器界面设计方案

> **状态：** 设计提案（Council 审议通过）
> **日期：** 2026-06-13
> **版本：** v1.0
> **前提：** 本方案基于 [visual-editor-design.md](./visual-editor-design.md) v1.5 的架构模型 + Council 四轮评审

---

## 概述

本文档细化三个界面的设计：

| 界面 | 核心问题 |
|------|---------|
| **代码块界面** | 唯一的逻辑代码块——如何呈现、添加、编辑？端口如何从代码自动生成？|
| **状态管理界面** | signal/computed/Store 如何可视化？运行时值如何查看？数据流如何追踪？|
| **事件系统界面** | 事件如何连线？处理如何创建？fn 调用如何可视化？|

> **设计原则：** 代码块只有一种——它是"写逻辑代码的容器"。signal/computed/Store 不是代码块，它们属于状态管理系统，有各自的界面设计。

---

## §1 代码块界面

### 1.1 唯一类型：逻辑代码块

**画布上只有一种代码块：逻辑代码块（💻）。** 它不是 signal、不是 computed、不是 Store——那些属于状态管理（§2）。代码块的职责只有一个：容纳一段可执行的逻辑代码，输入和输出通过端口与外界连接。

```
┌─ 💻 handleSubmit ────────── [－] ┐
│                                  │
│  ┌─ 输入 ─────────────────────┐  │
│  │ ● event : MouseEvent       │  │  ← 从代码参数自动生成
│  └────────────────────────────┘  │
│                                  │
│  ┌─ 输出 ─────────────────────┐  │
│  │ ● result : bool            │  │  ← 从 return 语句自动生成
│  └────────────────────────────┘  │
│                                  │
│  双击编辑源码                     │
└──────────────────────────────────┘
```

**代码块 ≠ 状态。** 代码块是行为（action/function/handler），状态（signal/computed/Store）由状态管理系统提供独立的可视化。

**代码决定端口：** 用户不选"块类型"。他们添加一个空白代码块，在 CodeEditorPopup 中写代码。保存后端口从代码自动提取。这和当前 `syncBlockFromSource` 机制一致。

### 1.2 添加代码块

**两种方式：**

- **空格键** → 搜索面板输入 "添加代码块" 或直接按 Enter → 空白代码块出现在画布
- **右键画布空白** → 菜单 "➕ 添加代码块" → 空白代码块出现在画布

```
右键菜单:                          空格搜索面板:
┌──────────────┐                  ┌─ 搜索 ──────────────┐
│ ➕ 添加代码块  │                  │ 🔍 [代码块       ]   │
└──────────────┘                  │                     │
                                  │ ➕ 添加代码块        │ ← 唯一选项（目前）
                                  │   编写逻辑代码       │
                                  └─────────────────────┘
```

因为只有一种块，搜索面板目前只有一个结果——但随着系统扩展（未来可能有"测试块"、"注释块"等），搜索面板的价值会体现。

**新块默认状态：**
- 名称：`newBlock`（可重命名）
- 端口：`value:out:any` + `call:in:any`（初始缺省端口）
- 源码：默认模板（空 action）
- 位置：画布左侧代码区，自动排列

### 1.3 默认源码模板

新代码块创建时，`source` 字段填充默认模板：

```
// 逻辑代码块
// 输入端口从参数自动生成，输出端口从返回值生成

action handleEvent(event) {
    // 在此编写事件处理逻辑
    
}
```

用户保存后，`syncBlockFromSource` 提取：
- 块名：`handleEvent`
- 输入端口：`event : any`
- 输出端口：`result : void`

如果用户改为 `action handleSubmit(event: MouseEvent) -> bool { return true; }`，则端口更新为：
- 块名：`handleSubmit`
- 输入端口：`event : MouseEvent`
- 输出端口：`result : bool`

### 1.4 块标签

**格式：** `💻 name → runtimeValue`（如果有返回值）

```
💻 handleSubmit → true
💻 handleEvent           ← 无返回值时不显示 →
💻 newBlock              ← 未保存时用默认名
```

**规则：**
- 图标固定为 💻
- 名称来自源码中 `action/fn name` 提取
- 返回值从 `evaluateDataFlow` 或 `setBlockValue` 获取
- 不显示 typeAnnotation（代码块的类型是其函数签名，不是单一类型标注）

### 1.5 端口

**端口完全由代码决定，不由块模板决定。**

```
端口形状: 圆形
输入端口: 左侧（函数参数）
输出端口: 右侧（返回值）

端口颜色 = TYPE_COLORS[type]
  any    → #6B7280 (灰)
  i32    → #2563EB (蓝)
  f64    → #059669 (绿)
  bool   → #D97706 (黄)
  String → #DB2777 (粉)
  void   → #9CA3AF (浅灰，输出端口无值)
```

**初始端口（新块，未保存代码前）：**

| 端口 | 方向 | 类型 | 说明 |
|------|------|------|------|
| call | in | any | 通用调用入口 |
| value | out | any | 通用返回值 |

**保存后的端口（从代码自动提取）：**

`syncBlockFromSource()` 从源码中提取：

| 源码模式 | 输入端口 | 输出端口 |
|---------|---------|---------|
| `action name(p1: T1, p2: T2) { ... }` | `p1 : T1`, `p2 : T2` | `result : void` |
| `action name(p1: T1) -> R { return ... }` | `p1 : T1` | `result : R` |
| `fn name(p1: T1) -> R { return ... }` | `p1 : T1` | `result : R` |
| 多参数 | 每个参数一个端口 | 一个返回值端口 |
| 无参数 | 只有 `trigger : void` 输入 | `result : 返回类型` |

**端口动态更新流程（已实现）：**
1. 用户在 CodeEditorPopup 中修改源码 → Ctrl+S 保存
2. `syncBlockFromSource()` 正则提取参数名、类型、返回类型
3. `setElementPorts()` 更新 Zustand
4. FlowCanvas sync 循环检测 port JSON 变化 → 移除旧 Rete 节点 → 用新端口重建

### 1.6 折叠

**手动折叠，不自动折叠。**

```
展开态:                            折叠态:
┌─ 💻 handleSubmit ──── [－] ┐    💻 handleSubmit → true
│ ● event : MouseEvent       │
│ ● result : bool            │
└────────────────────────────┘
```

**规则：**
- 右上角 `[－]` / `[＋]` 折叠按钮
- 折叠后 compact chip 显示：`💻 name → value`
- 不因连线数量自动折叠（无连线时最需要看到端口）
- 折叠状态保存到 `ElementData.isFolded`
- 有连线时仍可折叠，连线保持

### 1.7 名称

**代码块的名称来自源码。** 用户在代码中写 `action handleSubmit(...)` → 块名自动为 `handleSubmit`。

**规则：**
- 新块默认名：`newBlock`
- 保存源码后从 `action/fn name` 正则提取真实名称
- 如果同一画布有多个同名代码块 → 标签上显示 ID 后缀：`💻 handleSubmit (2)`
- 重命名在源码中修改函数名 → 保存 → 块名自动更新

### 1.8 删除

**删除代码块 → 所有相关连线变红断裂。** 行为与 §3.6 的孤儿处理一致：
- 连线变成红色虚线
- 侧面板聚合失效连线
- 用户必须手动修复——不自动重建、不静默删除

### 1.9 节点控制器——代码块的容器

**节点控制器（Node Controller）是代码块的作用域容器。** 每个组件/文件对应一个节点控制器。

```
┌─ 节点控制器: App ─────────────────────────────────────────────┐
│                                                               │
│  ┌─ 外部代码块（控制器级函数/库）──────────────────────┐      │
│  │                                                    │      │
│  │  📦 formatPrice(price: f64, currency: String) → String    │
│  │  📦 validateEmail(email: String) → bool            │      │
│  │  📦 debounce(fn, delay: i32) → void                │      │
│  │                                                    │      │
│  │  [＋ 添加外部代码块]                                 │      │
│  └────────────────────────────────────────────────────┘      │
│                                                               │
│  ┌─ 画布代码块（可引用外部代码块）──────────────────────┐      │
│  │                                                    │      │
│  │  ┌─ 💻 handleSubmit ──────┐  ┌─ 💻 onInput ──────┐ │      │
│  │  │ ← event : MouseEvent   │  │ ← value : String  │ │      │
│  │  │ → result : bool        │  │ → result : void   │ │      │
│  │  │                        │  │                    │ │      │
│  │  │ 调用: formatPrice()    │  │ 调用: debounce()   │ │      │
│  │  │       validateEmail()  │  │                    │ │      │
│  │  └────────────────────────┘  └────────────────────┘ │      │
│  │                                                    │      │
│  │  [＋ 添加代码块]                                     │      │
│  └────────────────────────────────────────────────────┘      │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

**三层结构：**

| 层级 | 概念 | 类比 | 位置 |
|------|------|------|------|
| **节点控制器** | 作用域容器，拥有一组代码块 | Unreal Blueprint 的 Event Graph 页面 | 整个画布 |
| **外部代码块** | 可复用的函数/库，供画布代码块调用 | Unreal Function Graph、Unity Subgraph | 控制器顶部区域（可折叠） |
| **画布代码块** | 逻辑节点，处理事件/数据流 | Unreal Event Graph 里的节点 | 画布主区域 |

### 1.10 外部代码块

**外部代码块是可复用的纯函数/库。** 它们独立于画布连线，不直接参与事件路由，而是被画布代码块在源码中调用。

```
┌─ 📦 formatPrice ────────────────────────────────────┐
│                                                      │
│  fn formatPrice(price: f64, currency: String) → String {  │
│      return currency + " " + price.toFixed(2);       │
│  }                                                   │
│                                                      │
│  被 3 个代码块引用:                                    │
│  · 💻 handleSubmit                                   │
│  · 💻 displayTotal                                   │
│  · 💻 sendReceipt                                    │
│                                                      │
│  [编辑] [删除]                                        │
└──────────────────────────────────────────────────────┘
```

**规则：**
- 外部代码块**不直接参与画布连线**——它是定义，不是调用
- 从函数库面板**拖入画布** → 创建 📞 调用节点（见 §3.3 详细设计）
- 画布上同一个 fn 可以有多个独立的调用节点——每个有各自的实参
- 外部代码块的"存在"显示在控制器顶部函数库面板（可折叠）
- 添加方式：右键函数库空白 → "添加函数"，或直接写 `fn name() { }` 代码
- 删除外部代码块时，检查所有引用它的调用节点 → 侧面板显示"以下调用节点引用了已删除的函数"
- **这就是 fn 的正确位置**——设计文档 v1.5 说 fn 不作为画布块（多调用点阻抗失配），但 fn 需要一个"家"。外部代码块区域就是 fn 的家，画布上的调用节点是 fn 的"使用"

**外部代码块 vs 画布代码块：**

| | 外部代码块 | 画布代码块 |
|------|------|------|
| 对应 OmniLang | `fn` | `action` |
| 可被复用 | ✅ 被多个画布代码块调用 | ❌ 独立逻辑单元 |
| 在画布上 | ❌ 不显示为连线节点 | ✅ 显示为连线节点 |
| 有端口 | ❌（参数通过代码调用） | ✅ 参数→输入端口，返回值→输出端口 |
| 参与事件路由 | ❌ | ✅ 接收事件连线 |
| 所在区域 | 控制器函数库面板 | 画布主区域 |
| 编辑 | 双击 → Monaco 编辑器 | 双击 → Monaco 编辑器 |

### 1.11 代码块调用外部函数——视觉表示

当画布代码块调用外部函数时，不创建连线，而是：

1. **代码块体内显示调用列表**（折叠行）
2. **在侧边检查面板中显示完整的调用图**

```
┌─ 💻 handleSubmit ────────── [－] ┐
│ ● event : MouseEvent            │
│ ● result : bool                 │
│ ┌─ 调用 ────────────────────┐   │
│ │ 📦 formatPrice(9.99, USD) │   │  ← 调用列表（只读）
│ │ 📦 validateEmail(email)   │   │
│ └───────────────────────────┘   │
│ 双击编辑源码                      │
└─────────────────────────────────┘
```

**规则：**
- 调用列表从源码解析——`syncBlockFromSource` 检测代码中的 `fnName(...)` 调用
- 列表项是只读的——要修改调用方式，在 Monaco 编辑器中改源码
- 点击列表项 → 跳转到外部代码块的源码编辑
- 如果外部代码块被删除 → 列表项变红 + 警告图标

### 1.12 代码块 vs 状态管理

| | 画布代码块（§1） | 外部代码块（§1.10） | 状态管理（§2） |
|------|------|------|------|
| 是什么 | 逻辑节点 | 可复用函数/库 | 数据容器 |
| 对应 OmniLang | `action` | `fn` | `signal`, `computed`, `Store` |
| 在画布上 | ✅ 连线节点 | ❌ 在函数库面板 | 待设计（§2） |
| 可被连线 | ✅ | ❌ | 待设计 |
| 端口来源 | 函数参数 + 返回值 | 无（通过代码调用） | 数据读写语义 |
| 图标 | 💻 | 📦 | ⚡ / 🔄 / 🗄️ |
| 编辑方式 | 双击 → Monaco | 双击 → Monaco | 待设计（§2） |

## §2 状态管理界面

### 2.1 核心架构：状态面板 + 画布节点

**双视图架构：**

```
┌─ 状态面板（左侧）──────────────────┐  ┌─ 画布 ──────────────────────────────────┐
│                                    │  │                                         │
│ 🔍 [搜索状态...              ]      │  │  ┌─ ⚡ count: i32 ────┐   ┌──────┐    │
│                                    │  │  │ → value : i32 = 5 │──→│ Text │    │
│ ┌─ 组件状态 ───────────────────┐   │  │  │ ← set : i32       │   └──────┘    │
│ │ ⚡ count : i32 = 5           │   │  │  └───────────────────┘               │
│ │    连到: Text.label          │   │  │        ↑                               │
│ │    来自: Button.onPress      │   │  │   ┌──────┐                            │
│ │                              │   │  │   │Button│ onPress                    │
│ │ 🔄 total : f64 = 10.70      │   │  │   └──────┘                            │
│ │    依赖: count, price       │   │  │                                         │
│ │                              │   │  │  ┌─ 🔄 total: f64 ────┐ [只读]        │
│ │ [＋ 添加]                    │   │  │  │ ← deps             │              │
│ └──────────────────────────────┘   │  │  │ → value : f64      │              │
│                                    │  │  └────────────────────┘              │
│ ┌─ Store ─────────────────────┐   │  │                                         │
│ │ 🗄️ CartStore                │   │  │  ┌─ 🗄️ CartStore ────┐                │
│ │    ⚡ items : Array          │   │  │  │ · items : Array     │               │
│ │       连到: List.dataSource │   │  │  │ · count : i32 = 3   │               │
│ │    ⚡ count : i32            │   │  │  │ ← addItem(item)    │               │
│ │    ▶️ addItem(item)          │   │  │  │ ← removeItem(id)   │               │
│ │    ▶️ removeItem(id)         │   │  │  └────────────────────┘              │
│ │                              │   │  │        ↑                               │
│ │ [＋ 添加 Store]              │   │  │   ┌──────┐ onPress                    │
│ └──────────────────────────────┘   │  │   │Button│                            │
│                                    │  │   └──────┘                            │
└────────────────────────────────────┘  └─────────────────────────────────────────┘
```

**两层职责：**

| 视图 | 职责 | 类比 |
|------|------|------|
| **状态面板** | 创建、删除、查看、管理所有状态 | Unity Blackboard、UE My Blueprint |
| **画布状态节点** | 连线——把状态值传入组件、接收来自事件的状态更新 | Unity Get/Set Variable 节点 |

**数据流：** 状态面板中创建一个 signal → 自动在画布上出现对应节点（或手动拖入）→ 节点端口与组件/代码块连线 → 连线即数据流。

### 2.2 状态面板

**位置：** 代码模式左侧，文件浏览器下方
**内容：** 三种状态的树形列表

```
状态面板
├── 🔍 搜索框（模糊匹配名称、类型、Store 名）
├── 组件状态 (Component State)
│   ├── ⚡ count : i32 = 5
│   ├── ⚡ name : String = ""
│   ├── 🔄 total : f64
│   └── [＋ 添加 signal / computed]
│
└── Store (Global State)
    ├── 🗄️ CartStore
    │   ├── ⚡ items : Array
    │   ├── ⚡ count : i32
    │   ├── ▶️ addItem(item)
    │   └── ▶️ removeItem(id)
    ├── 🗄️ UserStore
    │   ├── ⚡ currentUser : User?
    │   └── ▶️ login(email, password)
    └── [＋ 添加 Store]
```

**面板中每个条目的交互：**

| 操作 | 触发 | 效果 |
|------|------|------|
| **拖入画布** | 拖拽条目到画布 | 创建对应的画布状态节点 |
| **双击** | 双击条目 | 打开代码编辑器（Monaco 弹窗），编辑该状态的源码 |
| **右键** | 右键条目 | 菜单：编辑源码 / 重命名 / 删除 / 查看所有连线 / 复制 |
| **悬停** | 鼠标停留 | tooltip 显示：类型、当前值、被哪些元素引用、最后修改时间 |
| **已拖入标记** | 条目旁小绿点 | 表示该状态已有画布节点（拖过就不再重复拖） |

### 2.3 创建状态

**两种创建方式：**

#### 方式 A：表单创建（主方式）

```
点击 [＋ 添加 signal / computed] →
┌─ 新建 Signal ─────────────────────────────┐
│                                            │
│  类型: [Signal ▾]  ← Signal / Computed    │
│                                            │
│  名称: [count         ]                    │
│  数据类型: [i32 ▾]    ← i32/f64/bool/String│
│  初始值: [0           ]                    │
│                                            │
│         [取消]  [创建]                      │
└────────────────────────────────────────────┘
```

**为什么不用代码编辑器创建状态：**
- 表单创建保证状态结构一致——名称、类型、初始值都有明确位置
- 避免用户写 `signal count: i32 = "hello"` 这种类型不匹配的代码
- 状态面板中的条目始终保持结构化，方便搜索、排序、批量管理
- 编辑已有状态的逻辑（如修改初始值）→ 双击面板条目 → 在表单中修改（不是自由代码）

#### 方式 B：从画布事件创建（自然触发）

**事件连线时可选创建新状态 + 选择是否传递事件组件的状态。**

```
场景 1: 选择"不传事件状态" → 只创建纯 action
Button.onPress ─────╳──────→ (拖到空白)
                         │
                         └→ 弹出面板
                            ○ 创建新的 action
                            ○ 绑定已有 handler
```

### 2.4 画布上的状态节点

**从状态面板拖入画布后，状态变成可连线节点。** 不同类型有不同端口。

#### Signal 节点

```
┌─ ⚡ count: i32 ──── [－] ┐
│                          │
│  ● → value : i32 = 5    │  ← 输出端口: 当前值（Get）
│                          │    连线到: 组件属性 / computed.deps / 代码块.call
│                          │
│  ● ← set : i32          │  ← 输入端口: 接收新值（Set）
│                          │    连线自: 事件.onChange / 代码块.result
│                          │
│  双击编辑源码              │
└──────────────────────────┘
```

**连线规则：**
- `value` → 输出到任意需要该值的端口
- `set` ← 接收来自事件端口（如 `Input.onChange: String`）或代码块 `result` 端口的输入
- 一个 signal 的 `value` 可以连到多个目标（一对多）
- `set` 可以接收多个来源（选择最后到达的值，或显示冲突警告）

#### Computed 节点

```
┌─ 🔄 total: f64 ──── [－] [只读] ┐
│                                  │
│  ● → value : f64 = 10.70        │  ← 输出: 派生值（只读，无 setter）
│                                  │
│  ● ← deps : any                 │  ← 输入: 依赖的 signal 值
│                                  │    连线自: price.value, quantity.value
│                                  │
│  表达式: price * quantity * 1.07  │  ← 计算表达式（从源码提取，只读显示）
│  双击编辑源码                      │
└──────────────────────────────────┘
```

**规则：**
- `[只读]` 标记——computed 不能被直接赋值
- 自动显示计算表达式摘要
- `deps` 端口接收依赖 signal 的 `value` 输出
- 依赖 signal 值变化 → computed 自动重算 → `value` 更新
- 一个 computed 可以依赖多个 signal（`deps` 端口可接多根线）

#### Store 节点

```
折叠态:                             展开态:
┌─ 🗄️ CartStore ──── [＋] ┐       ┌─ 🗄️ CartStore ──── [－] ┐
│                         │       │                          │
│ items(3), count: 3      │       │  ● → items : Array       │
└─────────────────────────┘       │       = [3 items]        │
                                  │  ● → count : i32 = 3     │
                                  │                          │
                                  │  ● ← addItem : (item)    │
                                  │  ● ← removeItem : (id)   │
                                  │                          │
                                  │  双击编辑源码              │
                                  └──────────────────────────┘
```

**规则：**
- **折叠态**显示内部 signals 的摘要（名称 + 值）
- **展开态**为每个内部 signal 显示一个输出端口，每个 action 显示一个输入端口
- 内部 signal 端口可连到组件（如同独立 signal）
- 内部 action 端口可接收事件连线（如同代码块的 `call` 端口）
- Store 节点在画布上通常只有一个——它是全局单例
- 如果同一 Store 的内部 signals 被多个组件引用，Store 节点居中，连线辐射出去

### 2.5 画布上是否有节点——"拖入"机制

**状态面板中的条目不自动显示在画布上。** 用户拖入画布才出现节点。这样画布不会因自动创建的状态而拥挤。

```
状态面板              画布
───────              ────
⚡ count    ←──→  拖入  →  ┌─ ⚡ count ────┐
⚡ name     (留在面板)     └──────────────┘
⚡ email    (留在面板)     ┌─ ⚡ email ────┐
                          └──────────────┘
```

**规则：**
- 新创建的状态只在面板中出现
- 拖入画布 → 面板中该条目旁出现小绿点（表示已拖入）
- 同一个状态可以被拖入多次（多个 Get 节点）——但通常一个就够了
- 画布上删除节点不影响面板中的状态（只删节点不删状态）
- 面板中删除状态 → 画布上所有对应节点变红断裂

**三层信息架构：**

### 2.7 状态重命名与删除

**重命名：**
- 在状态面板中右键 → 重命名 → 输入新名称
- 或者双击 → 打开 Monaco 编辑器 → 改 `signal newName: i32 = 0;` → 保存
- 所有画布节点自动更新标签
- 所有连线保持不变（连线通过 ID 引用，不是名称）

**删除：**
- 删除前弹窗：`⚠ "count" 被 3 条连线引用，删除后这些连线将失效。`
- 确认删除 → 状态从面板消失 → 画布上对应节点变红断裂
- 侧面板聚合失效连线

### 2.8 与代码块的关系

**状态节点 + 代码块节点 = 数据流图：**

```
事件触发                    数据处理                    状态更新
───────                    ──────                    ──────

┌──────┐  onPress  ┌──────────────┐  result  ┌──────────┐
│Button│──────────→│💻 handleSubmit│─────────→│⚡ count   │
└──────┘           └──────────────┘          │  ← set   │
                                             └──────────┘
                                                   │
                                             value │
                                                   ↓
                                             ┌──────┐
                                             │ Text │
                                             └──────┘
```

**典型流程：**
1. 用户点击 Button → 触发 `onPress` 事件（事件端口）
2. 事件连线到 💻 `handleSubmit` 代码块（逻辑处理）
3. 代码块处理完成后 → `result` 输出连到 ⚡ `count` 的 `set` 端口
4. `count` 值更新 → 其 `value` 端口输出新值
5. `value` 连线到 Text 组件的 `label` 属性 → UI 自动更新

**关键分离：**
- **状态（signal/computed/Store）不包含逻辑**——它们是纯数据容器
- **代码块包含逻辑**——它们处理事件、计算、API 调用
- **连线连接两者**——事件 → 代码块（call 端口），代码块 → 状态（set 端口），状态 → 组件（属性端口）

#### 选择器触发时机

| 时机 | 触发方式 | 作用 |
|------|---------|------|
| **连线时** | 将上游 `value` 输出连到需要数据输入的端口 | 自动弹出选择器（如果上游是复杂类型） |
| **属性绑定时** | 在属性面板中点击 `[🔗 绑定]` 按钮 | 打开选择器，浏览所有可用状态 |
| **编辑表达式时** | 双击 computed 节点的表达式区域 | 打开选择器辅助构建表达式 |
| **检查面板中** | 选中节点后，点击"连线"列表中的连线 | 查看/修改该连线使用的数据路径 |

#### 选择器行为规则

- 简单类型（i32/f64/bool/String）→ 不需要选择器，直接传值
- 复杂类型（Array/Object/Struct/User 等）→ 自动弹出选择器
- `any` 类型 → 先连线，运行时确定类型后再支持选择（或用户手动写路径）
- 选择器生成的路径以 OmniLang 通用语法表达（`user.name`），codegen 阶段翻译为各目标语法
- 已选择的字段路径显示在连线标签上：`user.name`（小标签在连线旁）
- 如果上游数据结构变化（字段被删除/重命名）→ 连线变黄警告"路径可能失效"

### 3.1 事件端口

**从 Component Protocol 元数据自动生成，硬编码零容忍。**

```
当前（硬编码，错误）:              目标（元数据驱动，正确）:
getPorts() {                       getPorts(el) {
  if (el.tag === "Button")           const meta = COMPONENT_PROTOCOL[el.tag]
    ports.push({name:"onPress"})     return meta.events.map(e => ({
  if (el.tag === "Input")              name: e.name,

}                                      type: e.payload || "void",
                                       label: `${e.name}: ${e.payload || "void"}`
                                     }))
                                   }
```

**Component Protocol 中的事件定义（示例）：**
```json
{
  "component": "Button",
  "events": {
    "onPress":    { "description": "点击事件", "payload": "MouseEvent" },
    "onHover":    { "description": "鼠标悬停", "payload": null },
    "onFocus":    { "description": "获得焦点", "payload": null },
```

```
┌─ Button ───────────┐
```

**事件端口颜色：** 统一使用事件端口专用色 `#DC2626`（红色系），与数据端口（类型色）区分。这是 Unity VS 的 control port vs data port 理念——事件端口是触发器，数据端口是值。

#### 选项对照表

| 选项 | 画布结果 | 何时使用 | 关联 |
|------|---------|---------|------|
| **创建新代码块 💻** | 新的 💻 节点 + 源码 stub | 需要命名的新处理逻辑 | 代码自动生成：`action name(event: PayloadType) { }` |
| **调用已有函数 📞** | 新的 📞 调用节点 | 已有 fn 可以处理此事件 | 从函数库面板选 fn，实参自动映射 |
| **绑定已有代码块 💻** | 连线到已有节点 | 复用已有处理逻辑 | 搜索已有代码块 |
| **绑定 Store Action 🗄️** | 连线到 Store 的 action 端口 | 事件直接操作 Store | 从 Store 列表选 action |
| **☑ 同时创建 signal** | 额外创建 ⚡ 节点 + 自动连线 | 事件值需要存储到状态 | 仅 payload 不为 void 时显示 |
| **绑定已有 signal** | 事件值直接写入已有 ⚡ | 跳过代码块，纯数据流 | 简单场景 |

#### 面板显示规则

- **事件无 payload（void/null）** → 隐藏"创建状态"区域，只显示事件处理选项
- **事件有 payload（如 String, MouseEvent）** → 显示"创建状态"区域；简单类型（String/i32/f64/bool）默认勾选，复杂类型（MouseEvent）默认不勾选
- **"调用已有函数"选项** → 函数列表从当前控制器的函数库（§1.10）获取
- **"绑定 Store Action"选项** → action 列表从状态面板的 Store（§2.2）获取
- **"绑定已有代码块"选项** → 代码块列表从画布已有 💻 节点获取

### 3.3 fn 的完整生命周期——定义 vs 调用

**核心模型：一个 fn 有一个定义位置（函数库面板），可以有多个调用位置（画布上的调用节点）。**

这是 v1.5 设计文档中"调用点阻抗失配"的解决方案：

```
设计文档 v1.5 的问题:
  同一个 fn formatPrice 被 3 个不同参数调用 →
  一个画布块无法同时表达三种参数来源

解决方案:
  定义 = 外部代码块（📦 函数库面板）  ← 唯一的定义
  调用 = 内联 fn 块（📞 画布节点）    ← 每个调用点独立一个节点
```

```
┌─ 节点控制器: ProductPage ──────────────────────────────────────────┐
│                                                                     │
│  ┌─ 函数库（定义）────────────────────────────────────────────┐    │
│  │                                                              │    │
│  │  📦 formatPrice(price: f64, currency: String) → String      │    │
│  │  📦 validateEmail(email: String) → bool                     │    │
│  │  📦 debounce(fn, delay: i32) → void                         │    │
│  │                                                              │    │
│  └──────────────────────────────────────────────────────────────┘    │
│                                                                     │
│  ┌─ 画布（调用）─────────────────────────────────────────────┐     │
│  │                                                            │     │
│  │  ┌──────┐  onPress  ┌─ 📞 formatPrice ─┐                 │     │
│  │  │Button│──────────→│ price: 9.99      │────→ Text       │     │
│  │  │"查看" │           │ currency: "USD"  │                 │     │
│  │  └──────┘           └──────────────────┘                 │     │
│  │                                                            │     │
│  │  ┌──────┐  onPress  ┌─ 📞 formatPrice ─┐                 │     │
│  │  │Button│──────────→│ price: ⚡total    │────→ Text       │     │
│  │  │"购买" │           │ currency: "EUR"  │                 │     │
│  │  └──────┘           └──────────────────┘                 │     │
│  │                                   ↑                        │     │
│  │                          total.value (来自 signal 连线)     │     │
│  │                                                            │     │
│  │  ┌──────┐  onChange  ┌─ 📞 validateEmail ─┐              │     │
│  │  │Input │───────────→│ email: input.value │──→ Badge     │     │
│  │  └──────┘            └────────────────────┘              │     │
│  │                                                            │     │
│  └────────────────────────────────────────────────────────────┘     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**一个 fn 定义 → 多个调用节点。** 每个调用节点是独立的——自己的实参、自己的连线、自己的位置。但它们都引用同一个函数定义。

#### 定义（外部代码块 📦）

位置见 §1.10。总结：
- 在控制器函数库面板中创建和管理
- 双击打开 Monaco 编辑器，写 `fn name(params) → ReturnType { ... }`
- 不参与画布连线，不显示为画布节点
- 可以被多个画布调用节点引用
- 修改定义 → 所有调用节点的端口自动更新（参数变了 → 端口变了）

#### 调用（内联 fn 块 📞）

**从函数库拖入画布创建调用节点：**

```
函数库面板                          画布
───────                            ────
📦 formatPrice  ──拖入──→  ┌─ 📞 formatPrice ──────┐
📦 validateEmail           │ ← price : f64         │
📦 debounce                │ ← currency : String   │
                           │ → result : String     │
                           └───────────────────────┘
```

**调用节点的外观：**

```
折叠态 (默认):                      展开态:
┌─ 📞 formatPrice(9.99,USD) ─┐    ┌─ 📞 formatPrice ──── [－] ┐
└─────────────────────────────┘    │                           │
                                   │ ● ← price : f64   = 9.99 │
连线中的样子:                       │ ● ← currency : String="USD"│
                                   │ ● → result : String      │
┌──────┐  onPress  ┌─ 📞 ──┐      │                           │
│Button│──────────→│format…│      │ 定义: 📦 formatPrice      │
└──────┘           └───────┘      │ [打开定义源码]             │
                                   └───────────────────────────┘
```

**调用节点的端口：**

| 端口 | 方向 | 来源 |
|------|------|------|
| 每个参数一个端口 | 输入（左） | 从函数签名的参数列表自动生成。类型 = 参数类型 |
| result | 输出（右） | 从函数返回类型自动生成 |

#### 实参的三种来源

```
┌─ 📞 formatPrice ──────────┐
│                            │
│ ● ← price : f64 = 9.99    │  ← 方式1: 字面量（直接在节点上填写）
│                            │
│ ● ← currency : String     │  ← 方式2: 连线（从上游 signal/代码块传入）
│     ↑                      │
│     └─ ⚡ selectedCurrency │
│                            │
│ ● ← discount : f64 = 0.1  │  ← 方式3: 默认值（函数定义中的默认参数）
│                            │      fn formatPrice(price, currency, discount=0.1)
└────────────────────────────┘
```

**规则：**
- 字面量直接在节点上编辑（点击参数值区域 → 输入框）
- 连线传入优先于字面量——如果参数端口有连线，字面量被忽略
- 默认值来自函数定义中的 `param = defaultValue`
- 折叠态显示所有实参：`formatPrice(9.99, USD, 0.1)`

#### 定义变更 → 调用节点自动更新

```
函数库中修改:
  fn formatPrice(price: f64, currency: String) → String
  改为:
  fn formatPrice(price: f64, currency: String, locale: String = "en") → String

画布上所有调用节点自动更新:
  ┌─ 📞 formatPrice ────────────┐
  │ ● ← price : f64 = 9.99     │  ← 不变
  │ ● ← currency : String="USD"│  ← 不变
  │ ● ← locale : String="en"   │  ← 新增端口（使用默认值）
  │ ● → result : String        │  ← 不变
  └─────────────────────────────┘
```

#### 调用节点 vs 代码块节点

| | 📞 调用节点（内联 fn 块） | 💻 代码块 |
|------|------|------|
| 对应 | 调用已有 fn | 定义新 action |
| 逻辑在哪 | 在函数库的 📦 定义中 | 在节点自己的源码中 |
| 端口来源 | 函数参数签名 | 源码解析 |
| 双击行为 | 打开函数库中的定义 | 打开 Monaco 编辑 action 源码 |
| 可复用性 | ✅ 同一 fn 可被多处调用 | ❌ 每个独立逻辑 |
| 典型场景 | `formatPrice(9.99, "USD")` | `handleSubmit(event) { ... }` |
| 拖入方式 | 从函数库面板拖入 | 右键/空格 → 添加代码块 |

#### 创建调用节点的三种途径

| 途径 | 操作 | 使用场景 |
|------|------|---------|
| **从函数库拖入** | 拖拽 📦 到画布空白处 | 需要调用已有函数 |
| **事件连线时选择** | 拖事件端口到空白 → 面板选"调用已有函数" | 事件直接触发一个函数调用 |
| **右键/空格** | 菜单"添加函数调用"→ 选择目标函数 | 独立创建一个调用节点 |

### 3.4 事件类型传播

**事件参数类型从 Component Protocol → 事件端口 → 代码块/调用节点端口，全程类型化。**

```
Component Protocol         事件端口              目标端口
Button.onPress             ● onPress              💻 handleSubmit
  payload: MouseEvent  →   : MouseEvent     →      call : MouseEvent
                                                代码块签名: handleSubmit(event: MouseEvent)

Input.onChange              ● onChange             📞 validateEmail
  payload: String      →    : String          →     email : String
                                                调用实参: validateEmail(input.value)
```

**规则：**
- 事件端口类型来自 Component Protocol 的 `events.{name}.payload`
- 连线时验证事件端口类型与目标端口类型兼容
- 💻 代码块的 `call` 端口类型从源码 `action name(event: MouseEvent)` 提取
- 📞 调用节点的参数端口类型从函数定义 `fn name(param: Type)` 提取
- 类型不匹配 → 红色断线 + tooltip："事件类型 MouseEvent 与目标端口类型 String 不兼容"

### 3.5 事件多播

**暂不支持。** 一个事件端口只能连到一个 handler。

**远期（M5）：** 可选支持多播——一个事件触发多个 handler（顺序执行）。但这需要解决：
- handler 执行顺序
- 某个 handler 失败的传播策略
- 画布上的视觉表示（N 条线从一个端口出来）

### 3.6 孤儿与断线处理

**handler 被删除 → 连线变红断裂 + 侧面板出现"失效连线"警告。**

```
┌──────┐    onPress     ┌─ ⚠ 失效 ─┐
│Button│ ─── ═ ═ ═ ─── │ handleSubmit│  ← 红色虚线
└──────┘                │ (已删除)   │
                        └───────────┘

侧面板:
┌─ 失效连线 ────────────────────────────────┐
│ ⚠ 1 条连线失效                             │
│                                            │
│ Button.onPress → handleSubmit (已删除)      │
│ [重新绑定] [删除连线]                       │
└────────────────────────────────────────────┘
```

**规则：**
- 删除 💻 代码块 / ⚡ signal / 🔄 computed / 📞 调用节点时，所有相关连线变红断裂状态
- 断裂的连线在画布上显示为红色虚线
- 目标端显示 `⚠ 失效` 标签
- 侧面板聚合所有失效连线
- 用户必须手动修复——不自动重建、不静默删除

### 3.7 Component Protocol 变更时的连线迁移

**通过 UUID 而非显示名来标识事件端口。** 当协议升级时（如 `onPress` → `onClick`），通过 UUID 匹配保留连线。

```
Component Protocol:
{
  "events": {
    "onPress": {
      "id": "evt-btn-press-001",     ← 稳定 UUID
      "name": "onPress",
      "payload": "MouseEvent"
    }
  }
}

Wire 存储:
{
  fromPort: "evt-btn-press-001",     ← 引用 UUID，不是名字
  ...
}
```

**协议升级时：**
- 如果 UUID 匹配但名称变了 → 自动更新连线标签
- 如果 UUID 不再存在 → 连线变红断裂，侧面板提示"事件端口不再存在（可能在协议升级中移除）"
- 如果 payload 类型变了 → 连线保持但显示黄色警告"类型可能不兼容：MouseEvent → TouchEvent"

## §5 与现有设计文档的关系

本文档是 [visual-editor-design.md](./visual-editor-design.md) v1.5 的细化，覆盖其中的：
- §3.4 连线画布——连接逻辑的主编辑界面
- §3.4.1 画布代码块——signal/computed/Store 的端口化节点
- §3.5 逻辑分类学——什么在画布、什么在代码
- §3.6 实时状态检查 HUD
- §4 代码编辑框 + 代码片段系统

**重大变更（与 v1.5 的不同）：**

| v1.5 | 本方案 | 理由 |
|------|--------|------|
| 4 块类型（signal/computed/Store/action）混在画布 | 代码块（💻）+ 状态节点（⚡🔄🗄️）分离。画布代码块只有一种 | 逻辑和状态是不同概念，分开管理更清晰 |
| fn 不作为画布块 | fn 在函数库（📦定义）+ 画布调用节点（📞调用） | 解决了"多调用点阻抗失配"——定义唯一，调用可多个 |
| 连线标签 `[fnName(args)]` | 📞 调用节点（折叠节点，参数端口化） | 字符串标签不可类型检查，无法可视化参数流 |
| HUD 浮动叠加层 | 右侧固定检查面板 | Unity/UE 都用面板不用叠加层；与画布布局冲突 |
| 事件端口 `type: any` | 事件端口具体类型（来自 Component Protocol） | 没有类型就无法验证 handler 签名和自动补全 |
| 自动折叠（无连线→chip） | 手动折叠按钮 | 无连线时最需要看到端口 |
| 右键菜单 4 项 | 右键 2 项 + 空格搜索面板 | 代码块只有一种，不需要按类型分菜单 |
| 状态在画布上直接创建 | 状态在面板中创建，拖入画布才出节点 | 状态管理和连线画布解耦 |
| 代码编辑器创建状态 | 表单创建状态（类型安全） | 避免结构不一致和类型错误 |

**保留不变（与 v1.5 一致）：**
- 连线表达"谁连接谁"，代码面板表达"数据怎么变"
- 画布-代码面板分治编辑策略
- Command 模式撤销/重做
- 端口类型兼容性规则
- 设计模式 / 代码模式双模式架构
- Component Protocol 元数据驱动
