## 1. 总纲：极佳体验 = 想法 → 落地的关卡全部消失

**产品本质**：OmniLang 是"意图语言"（用户表达"想做什么"，不写平台形状，ADR-054），而 Poiesis 现在是"意图语言的**文本**编辑器"——语言是意图级的，编辑却是文本级的。**这个错位就是"带编译预览的文本编辑器"的本质**。全部设计任务 = 消除错位：让语义全集里每一条用户可表达的意图，都有一个一等公民的可视化表面。

**一句话**：用户面对的唯一对象是**他的应用**；编辑器的一切结构都是应用结构的投影；让想法到落地的每一个关卡都消失。

不会写代码的人（目标用户 = 半专业 B + 非技术 C，视觉优先）做一个应用，卡住他的只有四件事：

| 关卡 | 拆法 |
|---|---|
| **不会用** | 没有空白的开始：一句话孕育骨架；组件库 = learn-omniview 42 个活 demo |
| **接不上数据** | 内容长在界面上，"接数据"这个动作不存在（§6） |
| **怕弄坏** | 时间树分支 = 有保险的冒险；错误只长在发生处（§8） |
| **想不出来怎么做** | 语言即界面：编辑器结构 = 语言结构，UI 上的每个词都是语言里的词（§10） |

**"舒服"的四条判据**：
1. 不离开上下文——编辑与所见同一视口
2. 每个概念只有一张脸——一个语义不在多处编辑
3. 错误在发生处显示——语义验证三态直接渲染在对象上
4. 概念与语义 1:1——用户永远看不到 div/CSS/DOM，只看到组件/属性/token/意图

## 2. 全景：一对象 · 四透镜 · 一车间 · 一树

```
                 ┌─────────────────────────────┐
                 │      你的应用（活的对象）       │
                 │  打开 Poiesis = 打开应用本身     │
                 └─────────────────────────────┘
   建造透镜(长什么样)  因果透镜(怎么反应)  内容透镜(有什么)  结构透镜(由什么组成)
   应用即编辑器        行为是对象的属性      内容活在界面上      应用的一生
   ──────────────────────────────────────────────────────────────
   车间（数据处理）= 逻辑的居民：数据页（客厅）↔ 函数节点（书房）
   时间树（元层）   = 撤销 / 版本 / 灵感存档 / 发布 / 协作
```

- **一个对象**：你的应用，活的。没有"编辑器外壳"、没有设计/运行模式——打开就是应用本身（用户认可："应用即编辑器，让用户想到什么，就能设计出来什么"）。
- **四透镜**：看同一个对象的四种尺度。**缩放是导航，不是切换；预览是默认，不是功能。**
- **一车间**：数据处理（§7）。
- **一树**：时间（§8），跨透镜的元层。
- **演进记录**：本设计的直接前身是"四张脸"（设计画布 / 数据面板 / 逻辑画布 / 内嵌预览），被用户否决（"你这个问题还是陷进去了"——模式化框架，用户心中没有这些抽屉），由四透镜取代。四张脸中的有效元素已并入：内嵌预览 → 应用即编辑器（无独立预览窗口）、事件→行为接线 → 因果透镜、@form/@load 绿地 → 内容透镜。

## 3. 建造透镜：长什么样（应用即编辑器）

- **无模式、直接操纵**：悬停浮现操作柄；选中浮现语境面板；拖动即改布局；双击文字即改文案；拖边角即改尺寸。摸到的就是最终用户摸到的。
- **语境面板替代固定侧栏**：选中什么浮现什么；面板结构 = 语言结构（语言加新属性，面板自动多一节）。什么都不选 → 应用的面板。
- **组件库是活的例子**：learn-omniview 的 demo 就是组件库，拖进来就能用、能改、能看它怎么做的。模板不是空壳，是活的生物。
- **空状态即引导**：空应用不是空白画布，是一句"从左边拖一个按钮，你的应用就出生了"。
- **文字即数据，数据即文字**：输入框打字 = 设默认值；绑了数据后打字 = 直接预览数据流变化。
- **状态预览开关**（杀手锏）：@load 的 loading/error/data、@if 分支、@for 空/非空——画布上直接切换预览态看每种状态怎么渲染。B/C 用户手动触发不了 loading/error，但这个开关让他们能调试三态渲染。
- **设备框抽象**：运行形态不约束设计（拍板 #4），画布预留手机/桌面设备框切换；预览不是独立窗口——**应用本身就是预览**。
- **代码是应用的 DNA**：它存在、可导出、可 diff、可版本控制（保住产出质量的底线），但用户不需要读它——就像人不需要读自己的基因。Monaco 降级为隐藏的专家出口：默认不可见，代码查看 / 专家模式再打开。

## 4. 因果透镜：怎么反应（行为是对象的属性，不是逻辑图）

> 用户认可原话："因果透镜：行为是对象的属性，不是逻辑图，将界面的逻辑可视化，让用户编写应用的逻辑的时候，会更加思维清晰"

- **行为卡**：逻辑附着在对象身上。选中按钮 → 语境面板里"它会做什么"一节，一个按钮的完整行为清单，像说明书。添加行为 = 自然语言规则卡：`当 [点击] → [把] [计数器] [加 1]`。填卡像填表，不像是画图。
- **时间流视图**：复杂对象的行为按发生顺序排开（"打开页面时 → 加载数据 → 显示骨架屏…"）——CodeFlow 的升华形态：不是流程图，是行为的时间线。
- **数据也是对象，也有行为**："当 [流水数据] 变化 → [自动] [重算统计]"。
- **状态条**：应用所有数据像仪表盘常驻一处；B/C 用户调试 = 拨动开关、改数值、看应用当场变。加载/错误/空态不是"要写代码处理的事"，而是三格填空："加载时显示 [骨架] / 出错时显示 [提示+重试] / 有数据时显示 [列表]"。
- **拖动类行为也是填空**："这个卡片 [可以拖动]，方向 [水平]，最远 [屏幕一半]，松手 [回弹]"——@drag 约束变成填空，不是参数。
- **跨组件事件链**：子组件事件 → 父组件事件 → store action 的可视化接线（现状缺口：EventsSection 能声明 event，但画布无连线建立链路）。导航"点这个按钮去那页"是结构层的画线，组件间行为链是这里的画线。

### 就地 vs 独立（逻辑的两档，一个连续的心智）

> 用户反问："我点一个 数字+1 的按钮，它就是数字加 1，难道也要过一遍车间吗？它明明就是个闭包就能实现的"

| | 就地（行为卡） | 独立（函数节点/数据页） |
|---|---|---|
| 心智 | "这个按钮点一下加 1" | "报名按项目分组的统计" |
| 驻留 | 对象的因果透镜里 | 应用树里（命名后成为居民） |
| 规模 | 一步逻辑 | 任意长度 |
| 复用 | 无 | 多处点名 / 参数口 |
| 语言 | action / computed | fn / getter / @load |

- **用户不选档，系统按需给档**：第一个"数字+1"就地住行为卡；同一逻辑第二处出现 → 系统问"要变成公共的吗？"——抽象/重构的收益自动到手，用户永远不学这两个词。
- 地界：一步就地；两步以上或第二处要用 → 就地自动"升级邀请"。
- 语言契约检查：就地↔独立的界 = 语言 action↔fn 的界。

## 5. 内容透镜：有什么（数据 = 内容 = 条目）

> 迭代结论（用户方向）：回到"开发时数据到底怎么被用"的根本——想法里有内容，内容要出现在界面上、要被收集和更新。**解法是让"接数据"这个动作本身消失。**

- **内容长在界面上**：没有"数据模型"这个词。往页面放一个列表 → 列表出生了：列 = 字段、行 = 内容，当场可改。改列、加行、删行 = 定义内容。
- **先呈现，后来源**：内容先以样例活着；来源是最后的问题、可选项（人话三选）：**我自己维护**（界面上直接改）/ **别人提交**（配一个收集入口）/ **从别处接**（给一个来源）。换来源不碰设计。
- **一处内容，多张面孔**：同一内容在首页是列表、详情页是卡片、统计页是图表——面孔各管样式，内容一处变、处处变。点一下内容 → "我出现在这 3 个地方"，点一下跳过去。**"数据多了脑子不乱"的答案：没有"管理所有数据"的地方，内容按"是什么"分散在应用里。**
- **呈现方式是一等公民**：列表旁边就是菜单："换个样子看：卡片 / 表格 / 柱状图 / 折线图 / 占比图"。筛选/排序/分组/统计也是菜单，是人的话（"只看上个月的""按分类分组""最底下显示总计"）。**数组能力变成菜单选项，用户永远不碰"处理数据"这个动作。**
- **收集 = 表单，表单 = 内容的口**：表单设计器 = 把字段拖进表单，收集入口就长好了；每个字段下面挂**规则卡**——"必填" / "范围 1-100" / "格式：邮箱"，规则是人的语言不是正则，错误文案也是填空。发布后内容还会长——应用是活的。
- **自己会算的字段**："剩余天数 = 截止日期 - 今天"。
- **内容不存在时的引导**：从用户摆好的呈现草稿问"这个内容还不存在，要创建它吗？"——内容从草稿里长出来。全程没有一个动作叫"接数据"。
- **否决记录**：外部数据"拖 Excel/CSV 导入"方案被用户否决（"为什么拖拽 Excel 表格？这些我觉得不是很妙"）——外部接入的具体形态待定。

**迭代教训**（防止未来重蹈，判据优先级与样式板块同等）：
- 第一版"数据卡（从哪来 / 用在哪）"被否——用户："回归到最根本的上面，在开发应用的过程中，数据或是内容到底是怎么在这开发过程中去使用的？""不能因为数据多了，用户的脑子就变乱了。或者是用户本来有一个想法需要用到数据，但是就卡在使用数据这个关卡上面。"——**数据层一切设计的判据 = "使用数据的关卡是否消失"**。
- 第二版（条目三合一 + Excel 导入）也被否；收敛 = 第三版（本节：内容长在界面上、先呈现后来源）。

## 6. 结构透镜：由什么组成（应用的一生）

> 迭代结论（用户方向）：不只 0→1 的架构设计，还要覆盖**后续维护与重构**——"让用户有一个想法就能立即去用应用实现，且落地过程体验极佳"。

**架构 = 应用的结构，且结构是可以动手术的。**

**迭代教训**：第一版"放大透镜 = 远看地图（鸟瞰 / 缩放导航）"被否——用户："放大透镜好像设计的不是很妙"。架构是用户最初列的三大能力之一（界面 / 逻辑 / 架构），**必须是"能设计的层"，不是查看器**——所以结构层的一切都是"手术"：出生 / 生长 / 演化 / 健康，每幕都可动手、都有保险。四幕：

**第一幕 · 出生**（0→1）：新建应用不是"新建项目"，是**孕育**——一句话（"我想做一个记账应用"）→ 骨架出生（几个页面、每种页面放什么、有哪些条目、页面怎么走）。骨架来自**器官库**：learn-omniview demo 拆解成的"应用器官"（列表页/表单页/详情页/仪表盘/设置页），拖进来就能用能改；也可以空白出生，骨架自己长。

**第二幕 · 生长**（地图 + 手术）：应用长大后，结构层 = 一张活地图——页面像岛屿，导航是岛间航线。地图上做的都是**结构手术**：增删页面、拖拽重排、**从按钮拉一条线到另一页**（"点这个去那页"——导航设计就是画线）、把重复卡片**合并成共享组件**（系统主动发现："这个卡片在 3 处重复，合并成一个？改一处三处都变"）、全局改主题色。

**第三幕 · 演化**（维护与重构 = 想法落地零恐惧）：重构最怕的不是干活，是怕弄坏。解法：**大动干戈默认发生在分支世界里**——
- 想法（"把整个应用改成深色电影感""三个页面合并成工作台"）→ **开一个分支**，主干安然无恙
- 分支里随便折腾，怎么都弄不坏
- 折腾完，主世界和分支世界**并排对照** → 满意**嫁接**回主干 / 不满意放弃
- 分支还能**单向偷师**：把分支里单独一个页面拖回主干
- 用户认可原话："时间之树…能跟我前面说的架构相结合。用户有什么想法想快速落地，直接开一个分支就可以把想法落地"

**第四幕 · 健康**（体检，维护的雷达）：跨页面视角的语义验证——"这个卡片在 3 处重复""这个表单还没接内容""这个页面的错误态没设计"。**每条提示 = 一个可执行的动作**（合并它 / 接内容 / 补错误态），点一下就是一次小手术。

四幕是同一个"应用"对象在不同生命阶段的样子，不是四个模式。**结构层的本质：应用整体是可以直接动手的对象，且永远有保险。**

## 7. 车间：数据处理（逻辑的一个家，两级）

> 用户最终裁定："旧地和那个什么车间是一起的，就是上下级关系。车间相当于是一个函数，旧地就相当于是个可视化的数据处理界面…函数是这个可视化数据编辑器的数据处理节点"
> 界面/处理分离在语言层早已成立（编译目标 = UI 三件套 + 纯逻辑四目标），编辑器只是**把语言结构显形**，不是发明新架构。

### 统一形象：逻辑是一个"活页面"，函数是它的书房

**可视化数据界面（数据页）** = 应用里的一个活页面：上面摆着真实内容（列表/卡片/图表/数值），直接操作——拖一个"分组控件"上去，内容当场变。起个名字（"报名统计"）→ 长进应用树，和页面/组件/条目并列，打开即用。**逻辑是应用的居民，不是后台的引擎；复用不是功能，是树的结构性质。**

**函数节点** = 数据页上的一个器官（格子）：逻辑复杂到可视化界面处理不了 → 在这页上开一个函数节点，把复杂逻辑扔进去。有门牌、有输入口、有输出口；打开 = 完整过程（工序带形态：进料 → 工序 → 出料）。

**客厅（简单、直观、直接摸）↔ 书房（复杂、正式、独处）——一个家，不是两个地方。**

### 升级 / 降级：一个动作

- 客厅内容"越来越复杂了" → **点一下** → 整组收进一个函数节点，客厅留下干净格子；函数里是完整过程（收进去的控件变成步骤清单，一样的形式，只是独立了）
- 函数里其实只是几个控件的事 → 点一下展开回客厅
- **升级/降级 = 换一种看法，不是换一个地方**。没有"去车间"的开关，只有"这一页想更简单还是更独立"的一念。

### 流水线（函数内部的工序形态）

- **进料口**：仓库内容 / 界面参数 / 外部来源 / 另一条流水线的成品（流水线可以吃流水线——复用自然长出来，用户不学"函数调用"）
- **工序带**：动词卡，拖来排序、点开配规则——挑出 / 排序 / 分组 / 汇总 / 加一列 / 合并 / 对每条做 / 分流（分拣口）/ 取外部 / 吃另一条流水线。规则是人的话，不是表达式
- **出料口**：回展厅（主要）/ 存档 / 触发另一条流水线
- **参数口**：留一个口（"按月份"），界面调用时从控件取值——同一份算法，多处使用
- **试机台**（心脏）：投样例 → 看产出 → 质检绿勾。保存几组样例当质检记录，每次改动后跑一遍。**正确性不靠读代码，靠看产出**

### 桥：接数据 = 点名

界面上一个列表 → 属性面板"内容" → "来自数据页" → **点名一条** → 出料结构（字段）立刻出现在列配置；参数口自动变成界面控件（月份 → 下拉框）。**接数据只有一个动作：点名。**

### 三个入口（想法 → 流水线，路程是直的）

1. **就地升级**：行为卡里两步逻辑 → "想让它变成公共的？"一键升格
2. **界面反向**：列表摆好 → "给它一个来源" → 没有现成的 → "用一句话创建一条"（`把报名 → 按项目分组 → 统计每组人数` 直接产出骨架）
3. **需求即流水线**：先想要什么输出，再倒推工序

### 车间的健康

"这条流水线被 3 个界面点名"（点开看谁在用）/ "这两条差不多，合并成一条？" / "很久没人点名了"。流水线也在时间树上分叉：**试新算法 → 开分支 → 同一组质检样例喂给新旧两条 → 并排看差异 → 嫁接/扔。算法试验的恐惧也归零。**

## 8. 时间树：跨透镜的元层

> 用户认可："每一步操作都自动落在时间轴上"这个设计不错；"时间之树，这次设计非常不错"（树 = 升华版时间轴）

- **主干 = 现实**，当前工作的地方
- **分叉 = 平行世界**：回到昨天改一个决定 → 世界分叉。两个版本并存、并排对比、随时**嫁接**（把 B 版的某个页面拖进 A 版主干）、随时放弃
- **果实 = 发布**：每次发布在树上结一个果，随时可摘；**发布 = 一个按钮，B/C 用户全旅程的终点是"链接能用"**
- **播放成长纪录片**：快进看应用从一句话怎么长成现在的样子，每一帧都是可玩的版本
- **协作** = 多人在同一棵树上各自开枝
- **想法落地闭环**：想法 = 分支，手术 = 在分支里做，对比 = 并排，落地 = 嫁接，放弃 = 扔，发布 = 果实，倒带 = 撤销

所有操作自动落树：没有保存按钮，没有撤销弹窗——树的隐喻就是撤销、是版本、是灵感存档、是试错乐园。

## 10. 设计契约（不留隐患的保证）

| 契约 | 内容 |
|---|---|
| **对象契约** | 产品只有五类对象：**应用 / 页面 / 组件 / 条目（内容） / 数据页（命名逻辑）**。所有视图都是投影。语言加新语义 → 对象多一个属性、面板多一节——**编辑器形态永远不会滞后于语言**。就地逻辑不是对象，是对象的属性 |
| **动作契约** | 每个编辑动作 = 一条意图；动作的历史 = .omni 文本。视觉与语义是同一个东西的两面——**不是"两个系统同步"，是"一个动作两种读法"** |
| **透镜契约** | 任何功能必须挂进某张透镜或某个对象属性；挂不进 = 设计缺陷，不许进产品。任何逻辑必须能归类为"就地"或"独立"之一 |
| **语言契约** | 编辑器不发明任何语言外概念。UI 上出现的每个词都是语言里的词（事件面板已语义化收敛的成果，延伸到全部 UI） |

**语言契约验证表**（设计概念 ↔ 语言语义，抽查）：

| 设计概念 | 语言对应 |
|---|---|
| 行为卡（就地逻辑） | action / computed |
| 数据页（命名逻辑） | fn / getter / @load |
| 工序带（动词卡） | 域 2 数组方法 |
| 内容（条目） | @store / 数据三态（域 9） |
| 收集 = 表单 | @form（域 8） |
| 状态预览开关 | 语义验证三态 / 值三态 |
| 角色外观 / 状态外观 | token（域 5）/ 语义事件（域 3）视觉对应 |
| 导航画线 | 域 C 路由（设计域 6） |

## 11. 与探路轨的对齐

- 官方范围：**设计画布面（布局界面效率 / WYSIWYG / 设计系统）+ CodeFlow UX（节点形态/交互/布局）**。本设计将其扩展为四透镜 + 车间 + 时间树；**@form/@load 可视化范式现在锁定 = 冻结前零迁移成本窗口**（域 8/9 登记中、语料零使用、编辑器未接——真正的绿地）。
- 三条硬约束（.omni 往返兼容 / 语法零变更 / 四链同步）：本设计全程遵守——所有表面都产出 .omni 文本，视觉与语义同源（动作契约）。
- **投入约束**：编译器主线优先，探索用每周剩余精力（roadmap 决策 13）——本设计以"设计文档 + Storybook 原型"形态推进，不抢占编译器主线。
- **先例**：ADR-075"语义化即切换，不留旧残留"——可视化操作产出的也应该是语义，不保留"视觉残留"（编辑器不得发明与语言语义不对应的中间形态）。
- 历史关联：docs/design/visual-editor-design.md v1.5（WYSIWYG 布局画布 + 事件→连线跳转）是 v5 决策的败方（败因 = 积木输入速度 vs 开发者打字）；**目标用户换成 B/C 后败因前提失效**，其交互细节仍是本设计的合法先例，原型阶段先消化再动工。
- 远期：样式体检 / 试衣间运行数据依赖 → post-冻结，先设计后落地。
