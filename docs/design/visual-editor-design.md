## §1 设计目标

### 核心理念

```
设计模式（Design Mode）              代码模式（Code Mode）
┌──────────────────────────┐    ┌──────────────────────────────┐
│ WYSIWYG 布局画布          │    │ 连线画布（Rete.js FlowCanvas）│
│ + 属性面板（事件→连线）    │    │ + 文件浏览器 + 块面板         │
│                          │    │                              │
│ 拖组件 → 调样式 → 设事件   │    │ 代码块(signal/computed/Store) │
│ 事件→创建连线→            │    │ 端口连线传值                  │
│    └─ 自动跳转代码模式    │    │                              │
│                          │    │ ★ 双击代码块 → 全屏代码编辑框 │
└──────────────────────────┘    └──────────────────────────────┘
```

**边界原则（三轮 Council 确认，参考 Unity Bolt / Unreal Blueprint 的教训）：**

> **可视化适合表达"连接"——谁触发谁、数据从哪来到哪去。连线画布是这类逻辑的*主编辑界面*。**
> **可视化不适合表达"计算"——算法、转换、条件分支。这些永远在代码编辑框中。**
> **画布上的"块"只用于天然单实例的数据源（signal/computed/Store）——不用于可能有多个调用点的 fn。**

因此：
- **设计模式 → 布局/样式完全可视化**（WYSIWYG 画布 + 属性面板 + 组件面板拖拽）
- **代码模式 → 连线画布为主界面**（Rete.js 连线画布占据主区域，左侧文件浏览器+块面板，右侧代码片段面板）
- **连接逻辑 → 连线画布上的一等编辑界面**（事件绑定、信号→属性、Store→组件——拖拽连线建立，不是只读覆盖层）
- **画布代码块 → signal/computed/Store 的端口化节点**（有输入/输出端口，连线即传值，双击弹出全屏代码编辑框。fn **不**作为通用块——见 §3.5）
- **代码编辑 → 全屏弹窗**（双击画布代码块弹出 CodeEditorPopup，含 Monaco 编辑器 + 代码片段面板。不是固定面板，是临时编辑弹窗，Esc 关闭）
- **计算逻辑 → 代码编辑框**（`fn`/`signal`/`store`/`computed` 写代码，代码片段库辅助）
- **简单状态操作 → 代码片段面板**（`toggle`、`increment`、`push`——不在画布上，但以命名片段形式存在，可拖到画布作为只读标签）

### 用户画像

| 角色 | 主要工作方式 | 对编辑器的需求 |
|------|-------------|--------------|
| UI 设计师 | 完全可视化操作 | 组件面板、属性面板、实时预览、设计令牌 |
| 前端开发者 | 代码 + 可视化混合 | 代码面板有智能提示，可视化布局加速搭建 |
| 全栈开发者 | 逻辑以代码为主 | 能快速检查生成的效果，不需要离开 IDE |

## §2 整体架构

### 2.1 源格式决策（关键）

**核心决策：编辑器主格式 ≠ `.omni` 文件。**

```
.omni.json  ←── 编辑器原生格式（结构化 AST 快照，编辑器读写此文件）
    │
    ├── 导出 → .omni（人类可读、git 可 diff、omnic build 可编译）
    │
    └── 导入 ← .omni（仅当 .omni.json 不存在，且 .omni 是编辑器生成的）
```

**为什么不直接编辑 `.omni`？**

这是 Critic 指出的"往返保真度"问题：

> 手写的 `.omni` 包含注释、个性化格式、编辑器不认识的结构。
> 编辑器打开手写的 `.omni` → 解析回内部图 → 再导出，这些信息必然丢失。
> 所以编辑器**只能安全地重开自己生成的 `.omni`**。

**解决方案：**

| 场景 | 行为 |
|------|------|
| 新建项目 | 编辑器创建 `.omni.json` + 导出 `.omni` |
| 打开编辑器生成的项目 | 读 `.omni.json`（精确还原编辑状态） |
| 打开手写 `.omni` 项目 | **只读预览模式** + 提示"转换为可视化项目" |
| 转换为可视化项目 | 解析 `.omni` → `.omni.json`，提示"以下信息将丢失：注释、自定义格式" |
| git 协作 | `.omni` 进入 git（可 diff），`.omni.json` 可选（大文件/二进制） |
| **多人同时编辑同一组件** | 组件级文件拆分：每个组件独立 `.omni` + 独立 `.omni.json`。确定性导出保证同一输入 → 同一输出。合并时先合并 `.omni`（文本 diff），再重新导入生成 `.omni.json` |

**语义合并策略（多人协作底线）：**

多人编辑同一组件时，`.omni` 是合并的真相源。`.omni` 导出器将不同声明（`view {}`、`style {}`、`fn {}`、`signal {}`、`store {}`）按稳定顺序排列，不重排无关块，不修改未被编辑的块。同一块内两人同时修改 → git 正常冲突标记 → 用户在代码面板中手动解决。不同块各自被不同人修改 → git 自动合并成功。

### 2.2 统一搜索索引

**问题：** 80 个组件 × 20 个文件 × 画布连线 × 设计令牌 × 数据连接器 = 5 个搜索表面。用户要找"那个蓝色的 Button 在哪里被调用了"需要跨所有这些表面。

**策略：** `.omni.json` 中维护搜索索引（组件名、prop 值、signal 名、token 引用、connector 端点）。每次保存时增量更新索引。搜索栏（Ctrl+Shift+F）跨 `.omni` + `.omni.json` + tokens + connectors 返回结构化结果。

| 搜索类型 | 索引源 | 示例结果 |
|---------|--------|---------|
| 组件名 | `.omni.json` component registry | `Button` — 定义在 `ui/Button.omni:3`，被 12 个组件引用 |
| prop 值 | `.omni.json` element props | `variant="primary"` — 出现在 8 个文件 |
| signal 名 | `.omni.json` signal declarations | `count` — 定义在 `Counter.omni:5`，被 3 个元素绑定 |
| 令牌引用 | tokens 文件 | `colors.primary` — 被 45 个组件引用 |
| 连线 | `.omni.json` wire topology | `onPress → handleSubmit` — 3 条连线 |
| 数据源 | connectors 配置 | `GET /todos` — 被 2 个 Store 使用 |

## §3 组件事件系统设计

### 3.1 事件模型全景

OmniLang 中一个组件的交互逻辑包含三种层次的"事件"：

| 层次 | 概念 | 例子 | 编辑方式 |
|------|------|------|---------|
| **事件声明** | 组件暴露什么事件 | `event onSubmit: FormData;` | 代码面板 |
| **事件绑定** | 事件连接到什么处理器 | `<Button onPress={handleClick}>` | 可视化（属性面板下拉选择） |
| **事件处理** | 处理器内部的逻辑 | `fn handleClick() { store.increment(); }` | 代码面板 + 代码片段 |

### 3.2 可视化事件绑定（核心交互）

在属性面板中，事件属性表现为一个**处理器选择器**：

```
┌─ Button 属性 ──────────────────────────┐
│                                         │
│  label        "提交"                    │
│  variant      primary            ▼      │
│  disabled     □                          │
│  ──────────────────────────────────      │
│  onPress      [handleSubmit    ▼] [＋]  │  ← 事件绑定
│  onHover      [无              ▼] [＋]  │
│  onFocus      [无              ▼] [＋]  │
│                                         │
└─────────────────────────────────────────┘
```

**点击 [＋] 的三种路径：**

| 路径 | 场景 | 生成代码 |
|------|------|---------|
| **从已有 fn 选择** | 组件中已定义了 `fn handleSubmit() { }` | `<Button onPress={handleSubmit}>` |
| **创建新的 fn** | 选"新建函数"→ 命名 → 编辑器打开代码面板 | `fn onButtonPress() { }` + 绑定 |
| **创建内联 fn** | 简单逻辑，选"内联函数"→ 写 1-3 行代码 | `<Button onPress={fn() { ... }}>` |
| **绑定 Store Action** | 选 store → 选 action | `<Button onPress={store.submit}>` |

### 3.3 数据绑定（双向绑定 / 单向数据流）

```
信号 → UI 属性（单向）
UI 输入 → 信号（双向，通过 bind: 语法）

可视化表达：

┌─ Input 属性 ──────────────────────────┐
│                                        │
│  placeholder  "输入姓名..."             │
│  type         text              ▼      │
│  bind:value   [name            ▼]     │  ← 双向绑定到 signal
│                                        │
│  ┌─ 数据流预览 ─────────────────────┐  │
│  │                                  │  │
│  │  signal name ───bind:value──→ Input │
│  │  Input ──onChange──→ name = value  │
│  │                                  │  │
│  └──────────────────────────────────┘  │
└────────────────────────────────────────┘
```

### 3.4 连线画布——连接逻辑的主编辑界面

连线画布**不是只读的数据流地图**。它是事件绑定、信号连接、Store 注入的**一等编辑界面**。

"可选"的含义：连线叠加层可以**切换显示/隐藏**（纯画布模式 vs 连线模式），但连接关系本身**始终在画布上创建和编辑**。

```
┌─────────────────────────────────────────────────────┐
│  连线画布（连线模式）                                 │
│                                                     │
│   ┌──────┐    onPress     ┌──────────────┐         │
│   │Button│ ──────────────→│ handleSubmit │  ← 点击跳转到代码面板
│   └──────┘                └──────┬───────┘         │
│                                  │ store.add(item)  │
│                                  ▼                  │
│   ┌──────┐    {count}      ┌──────────┐           │
│   │ Text │ ←────────────── │  signal  │           │
│   └──────┘                 │  count   │           │
│                            └──────────┘           │
│                                                     │
│   ┌──────┐  bind:value    ┌──────────┐            │
│   │Input │ ←─────────────→│  signal  │            │
│   └──────┘                │  name    │            │
│                           └──────────┘            │
│                                                     │
│  [切换：连线模式 ▣]  [＋ 新建连线]                    │
└─────────────────────────────────────────────────────┘
```

**连线编辑交互：**

| 操作 | 交互 | 结果 |
|------|------|------|
| 创建事件绑定 | 从组件的 `onPress` 端口拖出连线 → 放到已有 fn / 空白处 → 弹出菜单"选择已有 fn / 新建 fn / 内联 fn / Store Action" | 生成绑定代码，自动创建 stub（如选择"新建 fn"） |
| 创建信号绑定 | 从 signal 端口拖出连线 → 放到可绑定组件的属性端口 | 生成 `bind:value={signalName}` |
| 创建 Store 注入 | 从 Store 面板拖 Store 到组件 | 生成 `@store StoreName` 声明 |
| 创建计算依赖 | 从 computed 端口 → 拖到它依赖的 signal | 更新 computed 的 `deps` 列表 |
| 删除连接 | 点击连线 → Delete 键 | 移除绑定，但**不删除**目标 fn/signal |
| 查看处理器 | 点击连线上的 fn 标签 → 代码面板跳转到该函数 | 在代码面板中编辑内部逻辑 |
| 切换连线可见性 | 工具栏切换按钮 | 隐藏/显示连线层（纯画布预览模式） |

**连线不表达的内容：**

连线只表达"谁连接谁"。以下内容**不在连线上，在代码面板里**：
- 处理器内部的算法逻辑
- 条件分支
- 数据格式转换
- API 调用和错误处理
- 任何超过一行的计算

> **这里的"Visual Scripting"：** 连线画布是连接逻辑的可视化编辑界面。连接逻辑写完以后，连线的显示可以关掉（纯画布模式），但连接关系一直在。这和"只读覆盖层"的区别是——你不是在看一张地图，你是在地图上直接建造道路。

### 3.4.1 画布代码块——signal / computed / Store 的端口化节点

代码块是 signal、computed、Store signal、Store action 在画布上的**带端口可视化节点**。它们不是 Bolt 式的逻辑节点——内部逻辑依然是代码，端口只是数据流入流出的接口。

**核心原则：只有天然单实例的数据源才显示为块，fn 不在此列。**

| 类型 | 画布块 | 端口 | 理由 |
|------|--------|------|------|
| **signal** | ✅ | 输出：当前值（`⬤ count: i32`）<br>输入：setter（`⬤ set count`） | 单一真相源，天然唯一实例 |
| **computed** | ✅ | 输出：派生值（`⬤ total: f64`）<br>输入：依赖（`⬤ deps`，从依赖 signal 自动连线） | 纯数据流，无副作用，单一实例 |
| **Store signal** | ✅ | 输出：只读值（`⬤ items: Array`） | Store 全局单例，signal 唯一 |
| **Store action** | ✅ | 调用端口（`⬤ add(item)`） | 可被多个组件调用，但 action 本身是唯一的，调用即触发 |
| **fn** | ❌ | — | 多调用点问题：同一个 fn 被 3 个不同参数的 Button 调用 → 一个块无法同时表达三种参数来源。见 §3.5.1 |
| **@native** | ⚠️ 条件 | `@in`/`@out` 注释声明的端口 | 仅在 fn 内通过 `@in`/`@out` 声明时显示端口，块内部始终为代码 |

```
┌─────────────────────────────────────────────────────┐
│  连线画布（连线模式）                                 │
│                                                     │
│  ┌──────────┐           ┌──────────────────┐       │
│  │  signal  │── 9.99 ──→│                  │       │
│  │  price   │           │  computed        │       │
│  │  ⬤ →    │           │  totalWithTax    │──→ ┌──────┐
│  │  ⬤ set  │           │  ⬤ → f64        │    │Text  │
│  └──────────┘           └──────────────────┘    │label │
│        ↑                                        └──────┘
│   ┌──────────┐           ┌──────────────────┐       │
│   │  Store   │── items ──→│                  │       │
│   │  cart    │           │  computed        │       │
│   │  ⬤ items│           │  itemCount       │──→ ┌──────┐
│   │  ⬤ add  │←── onPress ──┤  ⬤ → i32       │    │Badge │
│   └──────────┘           └──────────────────┘    └──────┘
│        ↑                                │
│   ┌──────────┐                          │
│   │  Button  │── onPress ───────────────┘
│   │  "加入"  │  ← 连线标签: [store.cart.add(item)]
│   └──────────┘
│                                                     │
└─────────────────────────────────────────────────────┘
```

**块的交互行为：**

| 操作 | 块类型 | 行为 |
|------|--------|------|
| **双击块** | 所有 | **弹出全屏代码编辑框（CodeEditorPopup）**：含 Monaco 编辑器 + 右侧代码片段面板。显示该块的源码、输入/输出端口信息、运行时值。Ctrl+S 保存，Esc 关闭。保存后自动求值更新 outputValue |
| 拖拽输出端口 | signal / computed / Store signal | 拖出连线 → 放到组件属性端口 → 建立绑定 |
| 拖入输入端口 | signal（setter）/ Store action | 从组件事件端口拖线 → 放到 setter/action 端口 → 建立调用 |
| 无连线时 | 所有 | 块折叠为 compact chip：`⬤ count: i32 = 5`，不占画布空间 |
| 有连线时 | 所有 | 展开为完整方块，显示端口和连线 |
| 重命名（代码编辑框保存后） | 所有 | 块标签和连线自动更新——**代码是真相源，画布是视图** |
| 删除（代码编辑框删除源码后） | 所有 | 块消失，所有相关连线变成红色断裂状态，提示用户修复 |

**为什么 fn 不作为通用块？——"调用点阻抗失配"**

Critic 发现的根本问题：命令式代码的**调用点（call site）**语义无法映射到单例图节点。

```
// 同一个 fn 被 3 个不同参数调用：
fn formatPrice(price: f64, currency: String) -> String {
    return currency + " " + price.toString();
}

// 画布上 3 个调用点:
Button "查看"  onPress → formatPrice(9.99, "USD")
Button "购买"  onPress → formatPrice(total, "EUR")
Text   label   = formatPrice(refPrice, "CNY")
```

如果画布上只放一个 `formatPrice` 块：
- 3 条线从 3 个不同地方连入 → **哪个参数来源对应哪个调用点？无法区分。**
- 块展示的是"声明"而非"使用"→ **视觉化没有减少任何认知负担。**

如果画布上放 3 个 `formatPrice` 块（每个调用点一个）：
- 违反了"一个 fn = 一个块"→ **块变成了调用点的重复，失去了"代表 fn"的意义。**
- 那不如直接用连线标签：`──onPress──→ [formatPrice(9.99, "USD")]`

**结论：fn 通过连线上的调用标签表达，不在画布上显示为块。** 调用标签显示函数名和实参，点击跳转到代码面板。

### 3.5 逻辑分类学——什么在画布、什么在代码

并非所有"逻辑"都应该放在画布上。以下是两轮 Council 确认的分类原则：

```
              可视化编辑（画布）          代码编辑（代码面板）
           ┌─────────────────────┬─────────────────────┐
   连接    │ ① 事件 → 处理器绑定  │                     │
  (wiring) │   信号 → 属性绑定   │      （无）          │
           │   Store → 组件注入  │                     │
           │   计算 → 依赖声明  │                     │
           ├─────────────────────┼─────────────────────┤
   计算    │                     │  算法、条件、循环    │
(compute)  │      （空）          │  API 调用、异步     │
           │                     │  数据格式化          │
           │                     │  复杂状态转换逻辑    │
           └─────────────────────┴─────────────────────┘

  代码片段面板（辅助，非独立编辑界面）：
  ├── toggle / increment / push / remove（简单状态操作）
  ├── 表单验证模板
  ├── API 调用 + 错误处理模板
  └── 用户自定义片段
```

**分类判断原则：**

> 问："这个操作是关于*谁连接到谁*，还是关于*数据怎么变*？"
> 如果是"谁连接到谁"→ 画布。如果是"数据怎么变"→ 代码面板。

| 功能 | 分类 | 理由 |
|------|------|------|
| Button.onPress → handleSubmit | 画布（连线） | 纯连接 |
| Input.bind:value → signal name | 画布（连线） | 纯连接 |
| Store → 组件注入 | 画布（连线） | 纯连接 |
| computed → 依赖的 signals | 画布（连线 + 块） | 纯连接；computed 天然单实例 |
| signal 值传递 | 画布（块端口） | signal 天然单实例，端口化后连线即传值 |
| Store signal 读取 | 画布（块端口） | Store 全局单例，端口化后连线即传值 |
| Store action 调用 | 画布（块端口） | action 唯一，调用端口接受连线触发 |
| fn 调用（含多调用点） | 画布（**连线标签**） | fn 不作为块；连线标签显示 `fnName(args)` |
| `count = count + 1` | **代码片段** | 是计算，但足够简单→片段 |
| `toggle(isOpen)` | **代码片段** | 是计算，但足够简单→片段 |
| `items.filter(...).sort(...)` | 代码面板 | 复杂计算 |
| `await api.submit(data)` | 代码面板 | 副作用+错误处理 |
| `if x > 0 { ... } else { ... }` | 代码面板 | 控制流 |

**为什么简单状态操作不在画布上？**

Council Skeptic 的论证被接受：
- `count + 1` 写代码比连节点快。可视化没有增加价值。
- 如果 `+1` 有个节点，明天就有人要 `filter` 节点、`sort` 节点、`await` 节点 → 滑坡回全节点图。
- 简单操作作为代码片段，双击插入到代码面板。可以拖到画布上变成**只读标签**（"这个 handler：toggle + push"），双击跳转到代码面板。

**为什么 fn 不作为画布块？——"调用点阻抗失配"**

Council Critic 发现：命令式代码中 fn 的*声明*和*调用点*是两个不同的概念。画布上的图节点天然是"一个声明 = 一个节点"，但一个 fn 的多个调用点各有不同的实参——图无法同时表达"这个 fn 被调用了 3 次，每次参数不同"。这不是 UI 细节问题，是图模型和命令式语义之间的**根本阻抗失配**。详细论证见 §3.4.1。

### 3.6 实时状态检查 HUD

Pragmatist 提出的高 ROI 功能——不增加新交互模型，但让抽象连线变得可感知：

```
画布上选中 <Text test-id="counter"> 后：
```

## §4 代码编辑框 + 代码片段系统

### 4.1 设计哲学

**连线画布 = "Visual Scripting"。代码编辑框 = 写代码的地方。代码片段 = 写代码的加速器。**

三者分工：
- **连线画布（FlowCanvas）**：表达"谁连接谁"——事件绑定、信号连线、Store 注入、计算依赖。代码模式的主界面，占据中央区域。代码块（signal/computed/Store action）以带端口节点显示在画布上。
- **代码编辑框（CodeEditorPopup）**：双击画布上的代码块 → 弹出全屏编辑框。Monaco 编辑器（左侧）+ 代码片段面板（右侧）。编辑该块的源码，Ctrl+S 保存，Esc 关闭。保存时自动求值 runtime value 并更新画布节点标签。
- **代码片段（Snippets）**：写代码的加速器，不是代码的替代品。上下文感知的模板，双击插入，Tab 跳转占位符。可以拖到画布上变成只读标签。

### 4.2 代码片段系统

在代码面板中，提供**上下文感知的代码片段库**：

```
┌─ 代码面板: handleSubmit ──────────────────────────┐
│                                                     │
│ fn handleSubmit() {                                 │
│     // 在此编写逻辑                                  │
│ █                                                   │
│ }                                                   │
│                                                     │
├─ 代码片段 ──────────────────────────────────────────┤
│                                                     │
│ ┌─ 状态操作 ────────────────────────────────────┐  │
│ │  set signal = value      更新信号值            │  │
│ │  toggle signal           切换布尔信号          │  │
│ │  increment signal        递增数值信号          │  │
│ │  push to Array           追加到数组            │  │
│ └───────────────────────────────────────────────┘  │
│                                                     │
│ ┌─ Store 操作 ──────────────────────────────────┐  │
│ │  store.action()          调用 Store Action     │  │
│ │  store.action(payload)   带参数调用            │  │
│ │  read store.signal       读取 Store 状态       │  │
│ └───────────────────────────────────────────────┘  │
│                                                     │
│ ┌─ 控制流 ──────────────────────────────────────┐  │
│ │  if condition { }        条件分支              │  │
│ │  for item in list { }    循环                  │  │
│ │  while condition { }     条件循环              │  │
│ │  match value { }         模式匹配              │  │
│ └───────────────────────────────────────────────┘  │
│                                                     │
│ ┌─ 异步 ────────────────────────────────────────┐  │
│ │  async fn name() { }     异步函数              │  │
│ │  await promise           等待异步结果          │  │
│ └───────────────────────────────────────────────┘  │
│                                                     │
│ ┌─ 事件发射 ────────────────────────────────────┐  │
│ │  event name()            发射组件事件          │  │
│ │  event name(payload)     带数据发射事件        │  │
│ └───────────────────────────────────────────────┘  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 4.3 代码块的"乐高"模型

代码片段不是死的模板——它们**感知当前上下文**：

| 光标位置 | 可选片段 |
|---------|---------|
| `fn` 体内 | 状态操作、控制流、Store 调用、异步操作 |
| `store` action 内 | 信号更新（`this.count = ...` 语法提示）、异步 |
| `computed` 表达式内 | 纯计算表达式（`count * 2`、`items.length`） |
| `view { }` 内（插值 `{ }` 中） | 信号引用、格式化函数（`format_date`、`t`） |
| `@if` 条件内 | 比较表达式、布尔信号 |

### 4.4 用户自定义片段

开发者可以保存自己的常用模式为命名片段：

```yaml
# ~/.omnilang/snippets/validation.yml
- name: "表单验证"
  description: "检查必填字段并显示错误"
  template: |
    let isValid: bool = true;
    let errors: Array<String> = [];
    if ${1:field}.length() == 0 {
        errors.push("${2:字段名}不能为空");
        isValid = false;
    }
    if !isValid {
        ${3:errorSignal} = errors;
        return;
    }
  context: "fn_body"  # 只在 fn 内部可用
```

## §5 多框架代码注入机制

### 5.1 问题的本质

OmniLang 编译到 8 个目标。但当用户需要在**特定目标**中插入**平台原生代码**时（例如调用 React 的 `useRef`、Flutter 的 `AnimationController`），我们需要一个机制：

- 不破坏 `.omni` 的"write once"语义
- 在可视化编辑器中可以管理
- 其他目标不会因此编译失败

### 5.2 `@native` 块在编辑器中的呈现

**现有语法：**
```omni
@native(react) {
    const videoRef = useRef<HTMLVideoElement>(null);
}

@native(flutter) {
    final controller = AnimationController(vsync: this);
}
```

**编辑器中的呈现：**

```
┌─ 原生代码块 ─────────────────────────────────────┐
│                                                    │
│  目标框架: [React ▼]                               │
│                                                    │
│  ┌─ 代码 ────────────────────────────────────┐    │
│  │ const videoRef = useRef<HTMLVideoElement>(null); │
│  │ videoRef.current?.play();                 │    │
│  └───────────────────────────────────────────┘    │
│                                                    │
│  [＋ 添加其他目标的代码块]                          │
│  ▸ Flutter: (未定义 — 编译时跳过)                   │
│  ▸ Vue: (未定义 — 编译时跳过)                       │
│                                                    │
│  ⚠ 此代码仅在 React 目标中生效。                   │
│    其他目标编译时将跳过此块。                       │
│                                                    │
└────────────────────────────────────────────────────┘
```

### 5.3 `@native` 块的设计原则

| 原则 | 说明 |
|------|------|
| **显式目标声明** | 每个 `@native` 块必须明确标注目标框架名 |
| **编译时跳过** | 非目标框架的 `@native` 块在 codegen 阶段被静默跳过 |
| **类型桥接** | `@native` 块可以读取外层 OmniLang 变量的**名称**，但不负责任何类型安全保证 |
| **输入/输出注释** | 编辑器鼓励开发者在 `@native` 块首行添加注释说明输入和输出 |
| **数量限制** | 一个组件中 `@native` 块超过 3 个时，编辑器发出警告（提示可维护性风险） |

### 5.4 输入/输出注释规范

让 `@native` 块对可视化编辑器**半透明**：

```omni
// @in: videoUrl (String)
// @out: isPlaying (bool)
@native(react) {
    const videoRef = useRef<HTMLVideoElement>(null);
    const [isPlaying, setIsPlaying] = useState(false);
    useEffect(() => {
        if (videoRef.current) {
            videoRef.current.play();
        }
    }, [videoUrl]);
}
```

编辑器读取 `@in`/`@out` 注释，在画布上为此 `@native` 块显示**输入/输出端口**——可以和其他信号连线。块内部是不透明的，但边界是可见的。

### 5.5 替代方案：`@native` 的退化策略

每个 `@native` 块应该有一个**退化行为**声明：

```omni
// @fallback: skip  -- 无此目标时跳过（默认）
// @fallback: warn  -- 无此目标时编译警告
// @fallback: error -- 无此目标时编译错误
@native(react) {
    const ref = useRef(null);
}
```

这确保"write once"语义不被悄悄破坏——如果某个目标缺少关键的原生实现，编译器会明确告知。

## §6 生产就绪基础层——竞品缺口分析

竞品对标不是为了"加功能追上 XX"，而是回答一个问题：**FlutterFlow / Figma / Webflow 的用户忍受了哪些事——我们能不能让他们不再忍？**

以下是四轮 Council 确认的三层缺口优先级：

### Tier 0 — 没了就走的（第一小时就崩）

| # | 能力 | 现状 | 竞品对标 | 为什么是 dealbreaker |
|---|------|------|---------|---------------------|
| **T0-1** | **撤销/重做**（无限深度） | 设计文档未提及 | Figma 无限制 undo | 连线画布上误删一根线 → 没有 Ctrl+Z → 用户关掉编辑器再也不用 |
| **T0-2** | **Git 可 diff 的 .omni 输出** | `.omni` 作为导出制品，但未验证 diff 可读性 | 无工具真正做到 | 3 个开发者协作 → PR review 看 diff 是乱的 → 团队放弃工具回退手写代码 |
| **T0-3** | **画布性能**（50+ 组件不卡） | 设计文档未提及 | Figma WebGL 渲染 | 真实项目到 50 组件 + 100 信号连线 → 修改一个属性画布卡 500ms → "玩具"标签贴上了 |

**T0-1：撤销/重做架构**

```
撤销栈模型（每操作一条记录）:

操作: 拖拽 Button 到画布        → push("add_element", {id, parent, position})
操作: 修改 label="提交"          → push("set_prop", {id, prop, oldVal, newVal})
操作: 连线 onPress → handleSubmit → push("add_wire", {from, to, port})
操作: 删除连线                   → push("remove_wire", {from, to, port})
Ctrl+Z                          → pop → 反向执行 → 连线恢复

实现要点:
- 每个编辑操作封装为 Command（不直接修改 .omni.json，通过 Command pipeline）
- 撤销栈存储在内存中，不序列化到文件（避免 git 噪音）
- 深度无限制（非 20 步上限）
- 关闭文件时清空（接受丢失，和 Figma 行为一致）
```

**T0-2：Git 可 diff 的输出**

```
验证标准（.omni 文件的 diff 可读性）:

1. 修改 Button label "提交" → "确认"
   diff 应显示: - label="提交" / + label="确认"（一行 diff）
   不应显示: 整个 view {} 块重新排序

2. 添加一个 <Text> 元素
   diff 应显示: + <Text>...</Text>（新行插入）
   不应显示: 整个文件 reformat

3. 拖拽 Button 从位置 3 → 位置 1（仅改变顺序）
   diff 应显示: 元素顺序变更（两行移动）
   不应显示: 整个元素内容变了

实现要点:
- .omni 导出器保持元素声明顺序 = 画布布局顺序
- 不写入自动生成的 ID 或时间戳到 .omni 文件
- 不对非编辑区域做 reformat
- .omni.json 中的连线拓扑/画布坐标/折叠状态等编辑器元数据不进入 .omni
```

**T0-3：画布性能**

```
目标: 200 组件 + 300 信号连线 → 属性修改 < 50ms 反馈

策略:
- 虚拟渲染: 只渲染视口内 + 100px 缓冲区的元素
- 空间索引: R-tree 或四叉树加速碰撞检测和连线路由
- 脏标记: 每个组件标记 dirty，只重渲染受影响的元素
- 连线按需: 默认只显示选中元素的邻接连线（其余折叠）
- Web Worker: 语法检查/代码补全移到 Worker 线程，不阻塞主线程
```

### Tier 1 — 生产阻断（不能用来做真项目）

| # | 能力 | 现状 | 竞品对标 | 为什么是阻断 |
|---|------|------|---------|------------|
| **T1-1** | **响应式约束布局** | view 编辑未涉及 | FlutterFlow Auto-layout, Webflow flexbox | 做完 desktop 版 → 想切 tablet → 整个布局崩了 → 用户放弃 |
| **T1-2** | **设计令牌/变量** | 未涉及 | Figma variables, FlutterFlow theme | 改主色从 blue → green → 需手动改 20 个组件 → 第四次要改就疯了 |
| **T1-3** | **数据连接器** | signal/Store 存在但无外部数据入口 | FlutterFlow Firebase, Retool REST | 做了 todo app 很顺 → 要接真 API → 发现没有脚手架 → 退回手写 |

**T1-1：响应式约束布局**

```
不要: 像素定位（absolute position）       ← 这是毒药
要做: 约束式布局（constraint-based）      ← 这是正道

组件的布局属性:
┌─────────────────────────────────────────────┐
│  布局模式: [Column ▼]                       │
│  ┌─ Column ──────────────────────────────┐  │
│  │  gap: 16px                            │  │
│  │  padding: 24px                        │  │
│  │  align: [start ▼]   justify: [center] │  │
│  │  ──────────────────────────────────    │  │
│  │  响应式覆盖（可选）:                    │  │
│  │  @tablet (≤768px):  gap → 12px        │  │
│  │  @mobile (≤375px):  direction → column │  │
│  └───────────────────────────────────────┘  │
│                                             │
│  画布顶栏: [Desktop ▾] [Tablet] [Mobile]    │  ← 一键切换预览
└─────────────────────────────────────────────┘
```

**T1-2：设计令牌系统**

```
主题令牌定义（.omni.json 中或独立 theme.omni）:
```

**T2-1：可逆的代码所有权——竞品的阿克琉斯之踵**

```
FlutterFlow 用户的工作流:
  可视化搭建 (70%) → 导出代码 → 手改 (30%) → 需求变更 → 重新可视化搭建 (100%)
  ↑                                                           ↑
  第一次改的 30% 全部丢失                                     痛点在这里

OmniLang 编辑器要实现:
  可视化搭建 → 导出 .omni → 手改 .omni → 回到编辑器
                                            │
                                    编辑器检测到:
                                    ① 手改的部分 = "受保护区域"
                                    ② 可视化的部分 = 可继续编辑
                                    ③ 冲突的部分 = 提示用户选择

实现思路:
- .omni 中标记两个区域:
  // @editor: managed       ← 此区域由编辑器管理，可安全覆盖
  // @editor: hand-written  ← 此区域为手写，编辑器只读

- 用户在代码面板中修改 fn 体 → 自动标记为 hand-written
- 用户在画布上修改布局 → 只覆盖 managed 区域
- 两者重叠 → 弹出冲突解决面板（选择保留哪个版本）
```

## §8 关键风险与缓解

| 风险 | 严重度 | 缓解措施 |
|------|--------|---------|
| **往返保真度**：手写 `.omni` 无法被编辑器精确读回 | CRITICAL | 采用 `.omni.json` 主格式；手写 `.omni` 只提供只读预览；明确"转换"意味着信息丢失 |
| **画布-代码双向同步**：画布编辑连接拓扑（图），代码面板编辑函数体（AST），两者如果触及同一段 JSON 会产生冲突 | CRITICAL | **分治编辑策略**：画布编辑 `.omni.json` 中的 `view {}` 结构 + `@store` 声明 + 事件绑定表达式；代码面板编辑 `fn {}` body + `signal {}` init + `store {}` body。两者不碰同一段 JSON。如果用户删除代码中的 signal 而画布上有 8 条连线引用它 → 画布显示断裂连线警告，不自动修复 |
| **调用点阻抗失配**：命令式代码的多调用点语义无法映射到单例图节点（同一个 fn 被 3 个不同参数的 Button 调用） | HIGH | fn 不作为通用画布块；改用连线标签 `[fnName(args)]` 在每个调用点独立显示实参；每处标签独立、可点击跳转代码面板。signal/computed/Store 不受影响（天然单实例） |
| **N-to-M 蜘蛛网**：20 signals × 15 events = 300 潜在连接点，全部显示连线会导致画布不可读 | HIGH | 连线按需显示（选中元素时才显示其相关连线）；超过 5 条连线自动折叠为 "＋ N 条连线" 标签；连线模式默认只显示当前选中元素的直接邻接边 |
| **参数重命名导致连线断裂**：代码面板中重命名 signal/computed → 画布块端口名称过时 → 连线语义断裂 | HIGH | 画布块是代码的**视图**，代码是真相源。重命名后画布自动更新端口标签和连线。极端情况（删除端口对应的 signal）→ 连线变红断裂状态，提示用户手动修复 |
| **8 目标分化**：组件属性在不同框架间不一致（React `onClick` ≠ Flutter `onPressed`） | HIGH | 属性面板显示"通用属性"优先，框架特定属性折叠在"高级"区域；组件元数据协议声明每个属性的目标兼容性；连线端口使用通用事件名（`onPress`），codegen 阶段翻译为框架特定名 |
| **@native 块的可维护性**：大量原生代码块不可搜索/不可重构 | HIGH | 编辑器限制每组件 @native ≤ 3 个；`@in`/`@out` 注释强制半透明；重构时搜索替换所有 @native 块 |
| **画布-代码操作冲突**：用户同时在画布和代码面板修改了同一个事件绑定 | MEDIUM | 事件绑定只能在画布或属性面板编辑——代码面板中事件绑定表达式为只读（灰显）。这避免了冲突：连接拓扑的"源"在画布 |
| **画布性能不达标**：50+ 组件时属性修改延迟 > 100ms，连线画布渲染掉帧 | HIGH | M2 起引入虚拟渲染（只渲染视口内元素）、脏标记系统（只重渲染受影响组件）、R-tree 空间索引；目标 200 组件 < 50ms 反馈 |
| **无设计令牌导致样式漂移**：20 个组件各自硬编码颜色，改主色需手动逐个修改 | HIGH | M3 引入 theme { colors, spacing, typography, radius } 令牌系统；属性面板优先显示令牌列表；修改令牌值 → 所有绑定自动更新 |
| **团队协作断裂**：`.omni.json` 在 gitignore 中 = 单人工具，3 人同时编辑同一组件产生不可合并的冲突 | HIGH | M1 起验证 `.omni` 输出 diff 可读性；每个组件独立 `.omni` 文件；语义合并策略：`.omni` 是合并真相源，不同声明块各自编辑自动合并，同块冲突 git 标记手动解决 |
| **语义合并缺失**：Alice 在画布改布局，Bob 在代码面板改同一个 fn 体——合并后数据不一致 | HIGH | `.omni` 导出器按稳定顺序排列声明块，不重排不编辑的块；确定性导出保证同一 `.omni.json` → 相同 `.omni`；同一块内两人修改 → git 正常冲突；不同块各自修改 → 自动合并成功 |
| **编辑器和手写代码的协作** | MEDIUM | 明确推荐工作流：布局用编辑器 → 导出 `.omni` → 逻辑手写 → 不再回到编辑器（或接受信息丢失） |
| **Git diff 噪音**：`.omni.json` 包含布局坐标信息 | MEDIUM | `.omni.json` 默认加入 `.gitignore`；`.omni` 始终是干净的文本格式进入版本控制；连线拓扑存储在 `.omni.json` 中，不在 `.omni` 中

## §9 附录：Component Protocol 草案

可视化编辑器需要在 OmniView 内置组件的基础上，为每个组件提供**元数据描述**，以便属性面板知道该展示什么：

```json
{
  "component": "Button",
  "category": "Actions",
  "description": "可点击的按钮组件",
  "props": {
    "label": { "type": "string", "default": "Button", "editor": "text" },
    "variant": { "type": "enum", "values": ["primary", "secondary", "danger", "ghost"], "default": "primary", "editor": "select" },
    "disabled": { "type": "bool", "default": false, "editor": "checkbox" },
    "loading": { "type": "bool", "default": false, "editor": "checkbox" }
  },
  "events": {
    "onPress": { "description": "点击事件", "payload": null },
    "onHover": { "description": "鼠标悬停", "payload": null },
    "onFocus": { "description": "获得焦点", "payload": null }
  },
  "styleProperties": ["width", "height", "padding", "margin", "background_color", "border_radius"],
  "children": false,
  "targets": ["react", "vue", "dioxus", "flutter"]
}
```

这份元数据：
- 驱动属性面板的渲染（什么类型用什么编辑器控件）
- 声明事件列表（决定了事件绑定下拉选项）
- 声明样式属性白名单（哪些 CSS 属性对该组件有意义）
- 声明目标兼容性

## §10 设计总结

```
╔══════════════════════════════════════════════════════════╗
║  OmniLang 可视化编辑器的设计哲学                          ║
║                                                          ║
║  1. 可视化做"连接"——组件树、属性、事件路由、数据绑定      ║
║     连线画布是连接逻辑的*一等编辑界面*，不是只读覆盖层    ║
║  2. 画布代码块做"数据源"——signal/computed/Store 端口化    ║
║     天然单实例的数据源自动显示为可连线块，连线即传值      ║
║  3. fn 不做画布块——多调用点阻抗失配让它不适合图表达       ║
║     fn 调用以连线标签 [fnName(args)] 显示，点击跳转代码   ║
║  4. 代码做"计算"——业务逻辑、算法、数据转换                ║
║     代码面板 + LSP + 上下文感知，不在画布上画节点图       ║
║  5. 代码不是从零写——代码片段库提供"乐高块"                ║
║     简单状态操作在片段中，不在画布上                       ║
║  6. 生产就绪不是"以后再说"——撤销、diff、性能从 M1 开始    ║
║     Tier 0 → Tier 1 → Tier 2 渐进，不跳过基础层           ║
║  7. 设计令牌驱动样式——改一处，处处更新                     ║
║     theme { colors, spacing, typography } 是生产必需品     ║
║  8. 数据连接器做脚手架而非平台——生成代码，不托管数据      ║
║     REST/GraphQL/Firebase → 自动生成 Store + 类型定义     ║
║  9. 可逆的代码所有权——可视 → 代码 → 可视，不丢失工作       ║
```
