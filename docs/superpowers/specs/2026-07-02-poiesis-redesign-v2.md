> 设计日期：2026-07-02

## 1. 核心理念

Poiesis 是一个**架构优先**的 OmniLang 可视化编辑器。它的目标不是替代代码编辑器，而是让用户以**应用架构师**的视角工作：

- 看清应用的模块关系，管理功能耦合与模块内聚
- 识别与隔离"业务核心"与"技术细节"
- 在正确的抽象层次上做决策
- 底层代码细节在需要时才深入

**核心原则：图谱是地图，代码是目的地，画布是预览。**

## 2. 两大页面

Poiesis 分为两个主页面：**架构页面**（首页）和**设计页面**（标签页编辑）。

### 2.1 架构页面 —— 关系图谱首页

架构页面是 Poiesis 的默认首页，以 Obsidian 风格的关系图谱为核心。

#### 2.1.1 双层画布（按钮切换）

架构页面同样是双层画布，通过顶部按钮切换：

| 层 | 内容 | 作用 |
|----|------|------|
| **上层（界面预览）** | 整个应用的完整渲染（含样式和部分逻辑如 if 渲染，不含 Store 和其他复杂代码逻辑） | 所见即所得的应用预览 |
| **下层（关系图谱）** | Obsidian 风格的可展开泡泡节点图 | 管理和理解应用架构 |

两层之间同步选中：在图谱中选中界面泡泡 → 上层预览高亮对应 UI 区域；在上层选中 UI 元素 → 图谱中对应泡泡高亮。

#### 2.1.2 泡泡节点体系 —— 语义级节点

节点不按文件组织，而是按**语义概念**组织。类似 C4 模型，分层可用户自定义或系统预设。

**第一层（最缩小时）：三大类泡泡**

```
    ┌──────────┐     ┌──────────┐     ┌──────────┐
    │   界面    │─────│  Store   │─────│   代码    │
    │  (UI)    │     │ (State)  │     │ (Logic)  │
    └──────────┘     └──────────┘     └──────────┘
```

**三大泡泡联动规则：**
- 当"界面"泡泡展开时，对应的 Store 和代码泡泡也自动展开
- 被界面引用的 Store/代码节点高亮显示，靠近中心
- 无关的 Store/代码节点变灰，距离变远
- 连线标明具体关系：界面↔Store 显示具体读写（如 `items`、`add()`），界面↔代码显示具体调用

**"界面"泡泡内部层级：**
- 展开后显示所有 page/component 的泡泡
- 按组件嵌套关系展示：大组件包含子组件，连线表达组合关系
- 可层层展开——如果组件内部全是自定义组件，继续展开；如果包含基础元素（如 div、button），这就是最底层泡泡
- 界面画布中选中 UI 元素 ↔ 图谱中对应泡泡高亮，双向同步

**"Store"泡泡内部：**
- 全局 Store 文件内 signal、getter、action 各为子泡泡
- 不在整体架构中显示组件内部 inline store

**"代码"泡泡内部：**
- 全局代码（lib 中的 pub fn、struct、type alias 等）
- 可按函数作为子泡泡，或将函数集作为大泡泡实现分层
- 不在整体架构中显示组件内部 fn

#### 2.1.3 整体架构模式 vs 局部架构模式

这是一个**两级架构体系**，按先后顺序使用：

**整体架构模式（起点，全局视角）：**

- 默认进入的模式
- 只显示全局 Store + 全局代码 + 界面
- 回答："这个应用有哪些页面？哪些 Store？大致依赖全貌？"
- 最底层泡泡是组件（含基础元素的最底层）

**局部架构模式（深入，去中心化）：**

- 右键组件泡泡 → 选择"以该组件为中心"
- 手动切换，非自动激活
- 以该组件为中心重新布局，只显示相关节点
- 按需加载：不仅显示全局 Store/代码，也显示组件内部的 inline store、信号、自定义函数
- 回答："这个组件依赖了哪些数据？内部有什么逻辑？谁在使用它？"

**局部架构模式的圈层结构：**

围绕中心组件形成不同颜色的圈层：

| 圈层 | 颜色 | 内容 | 说明 |
|------|------|------|------|
| 接口层（外圈） | 🔵 蓝色 | props、events | 组件的对外承诺 |
| 组合层（中圈） | 🟢 绿色 | 父组件、子组件 | 组件的上下级关系 |
| 依赖层（连线） | 🔴 红色 | Store 数据读/写 | 组件的外部数据依赖 |
| 依赖层（连线） | 🟣 紫色 | lib/pub fn 调用 | 组件的代码依赖 |
| 内部层（展开可见） | ⚪ 灰色 | signal、computed、fn、style | 组件的私有实现 |

架构模式切换流程：
```
整体架构（默认首页）
    │
    │ 展开泡泡，探索依赖关系
    │ 确定要深入的具体组件
    ▼
局部架构（右键 → "以该组件为中心"）
    │
    │ 查看组件的完整周边关系
    │ 双击最底层组件泡泡
    ▼
设计页面（标签页编辑器）
```

#### 2.1.4 导航到设计页面

从架构页面进入设计页面的方式：
- 右键任意泡泡 → 选择"设计"
- 双击最底层元素泡泡（含基础元素如 div、button 的组件）
- 如果不是最底层（内部全是自定义组件），双击会进入该泡泡内部继续展开

进入设计页面后，打开对应 .omni 文件的标签页。

### 2.2 设计页面 —— 标签页编辑器

#### 2.2.1 标签页 = .omni 文件

- 每个标签页对应一个 `.omni` 源文件
- 关闭标签页 = 关闭文件
- 面包屑导航：显示当前文件路径，可回退到架构页面
- 从架构页面双击组件泡泡 → 打开对应文件的标签页

#### 2.2.2 双层画布（Z 轴纵深）

设计页面使用 Z 轴双层画布（上下层，非按钮切换）：

| 层 | 含义 | 显示内容 |
|----|------|---------|
| **上层（界面设计）** | "皮"——组件渲染后的样子 | 真实 DOM 渲染预览 |
| **下层（代码设计）** | "骨"——fn 内部逻辑结构 | 节点流（函数头 / 骨架 / 代码块 / return 等节点 + 连线） |

**交互方式：**
- **默认**：上层全屏显示组件渲染预览
- **单击组件/元素**：选中，右侧属性面板更新
- **双击组件**：上层缩小到画布一角，下层浮现——显示该组件的 fn 节点流图。相关节点高亮，不相关节点变灰
- **双击代码块节点**：下层节点流图替换为 Monaco 编辑器，编辑代码内容
- **面包屑导航**：点击面包屑可回退到上层全屏

#### 2.2.3 左侧面板

左侧面板仅保留两个面板：

| 面板 | 功能 |
|------|------|
| **组件面板** | 可拖拽到画布的组件列表（类似当前 poiesis 的 ComponentPalette） |
| **组件树面板** | 显示当前 .omni 文件的组件层级树（类似当前 poiesis 的 ComponentTree） |

其他所有面板（BlockPalette、StatePanel、ConnectorPanel、TokenPanel、SnippetPanel 等）全部移除。

**signal / prop / event 等定义**在左侧面板或右属性面板中管理，不在代码画布中作为节点出现。

#### 2.2.4 右侧属性面板

根据选中目标加载不同内容：

| 选中目标 | 显示内容 |
|---------|---------|
| **元素（div、button 等基础元素）** | 设置 ID（用户自定义）；CSS Class 绑定（样式在 style 块中定义） |
| **组件（自定义组件）** | ID + 组件自定义属性（props） |
| **事件绑定** | 绑定事件到自定义函数 |
| **样式填写** | 内联样式编辑 |

#### 2.2.5 代码画布 —— 节点体系

代码画布的职责是**编辑 .omni 文件中 fn 的代码逻辑**。所有节点平级：

| 节点类型 | 含义 | 说明 |
|---------|------|------|
| **函数头** | 节点流的入口 | 代表一个自定义函数的开始 |
| **骨架节点** | 控制流结构 | if / else / for / while 等，不含具体代码，仅作为"骨架" |
| **代码块节点** | 承载实际代码 | 双击 → Monaco 编辑器（语法高亮、自动补全、实时诊断） |
| **return 节点** | 节点流的出口 | |

- 一个自定义函数（带函数体节点的 fn）= 一条独立的节点流
- 一个组件里的多个自定义函数的节点流可共存于同一张画布
- 代码画布只显示与当前选中元素相关的节点流，无关节点流变灰

#### 2.2.6 Monaco 编辑器

- 双击代码块节点 → 下层节点流图替换为 Monaco（节点图缩小为侧边缩略图）
- 提供：语法高亮、自动补全（基于项目内 signal/computed/fn/type 名称）、实时诊断（调用编译器 WASM）
- 编辑完成后保存 → 内容写回代码块节点

## 3. 数据持久化

### 3.1 .omni 文件 —— 代码唯一真相源

.omni 文件保持**纯净可编译**，不包含任何 Poiesis 编辑器专属数据。

每个语义代码块前插入一行 PID 注释作为解析标签：

```omni
import omniview;
import { TodoStore } from "../stores/TodoStore";

// @pid:c1
component Counter {
    @store TodoStore;

    // @pid:c1_n1
    signal count: i32 = 0;

    // @pid:c1_n2
    computed doubled: i32 = count * 2;

    // @pid:c1_n3
    prop step: i32 = 1;

    // @pid:c1_n4
    fn inc() {
        count = count + step;
    }

    // @pid:c1_n5
    event onChange: i32;

    // @pid:c1_n6
    view {
        <div class: counter>
            <span>{count}</span>
            <button @onPress={inc}>+</button>
        </div>
    }

    // @pid:c1_n7
    style {
        .counter { display: flex; gap: 8px; }
    }
}
```

PID 粒度规则：
- component 前必须有
- store 前必须有
- 每个可独立操作的语义单元（signal、computed、prop、fn、event、view、style 等）前必须有
- store 内 signal/getter/action 前必须有
- lib 内 struct/type/pub-fn 前必须有

### 3.2 项目 JSON —— Poiesis 元数据

项目根目录 **单一** JSON 文件保存所有 Poiesis 编辑器元数据。

**JSON 保存的数据（直接从 .omni 解析不出的数据）：**
- 节点在画布上的位置（x, y）
- 节点之间的连线关系（from、to、端口类型）
- 节点的折叠/展开状态
- 画布的缩放/平移状态
- 面板尺寸和布局
- 架构页面图谱状态（展开/折叠的泡泡、模式选择等）

**JSON 不保存的数据（从 .omni 源码直接解析）：**
- signal 名称、类型、初始值
- fn 函数体代码（用户 Monaco 编辑，写回 .omni 文件）
- view 模板结构
- style CSS 内容
- import 依赖关系
- store 的 signal/getter/action 定义

**JSON 结构示意：**

```json
{
  "version": 1,
  "architecture": {
    "mode": "overall",
    "expandedBubbles": ["界面", "Store"],
    "focusComponent": null,
    "camera": { "x": 0, "y": 0, "zoom": 1 }
  },
  "nodes": {
    "c1": { "pos": { "x": 100, "y": 50 }, "folded": false },
    "c1_n1": { "pos": { "x": 120, "y": 80 }, "folded": false },
    "c1_n2": { "pos": { "x": 120, "y": 160 }, "folded": false },
    "c1_n4": { "pos": { "x": 120, "y": 240 }, "folded": false }
  },
  "wires": [
    { "from": "c1_n1", "fromPort": "value", "to": "c1_n2", "toPort": "deps" }
  ],
  "panels": {
    "leftWidth": 240,
    "rightWidth": 300
  },
  "canvasStates": {
    "Counter.omni": { "zoom": 1, "panX": 0, "panY": 0 }
  }
}
```

## 4. 编辑器布局

### 4.1 架构页面布局

```
┌──────────────────────────────────────────────────┐
│  工具栏（编译/运行/撤销/重做/缩放/模式切换：界面预览↔关系图谱）  │
├──────────┬────────────────────────┬──────────────┤
│ 项目文件树 │                        │  选中泡泡属性  │
│ (可折叠)  │    画布区域             │  (简要摘要)   │
│          │    (双层画布)           │              │
│          │                        │  选中: Counter │
│          │                        │  类型: 组件    │
│          │                        │  依赖: ...    │
├──────────┴────────────────────────┴──────────────┤
│  状态栏（编译状态 / 错误数 / 项目名）                 │
└──────────────────────────────────────────────────┘
```

### 4.2 设计页面布局

```
┌──────────────────────────────────────────────────┐
│  标签栏（TodoPage.omni / Counter.omni / ...）       │
├──────────┬────────────────────────┬──────────────┤
│ 组件面板   │                        │  属性面板     │
│          │    画布区域             │              │
│ 组件树    │    (双层画布)           │  ID / Props  │
│          │                        │  Events      │
│          │                        │  Style       │
├──────────┴────────────────────────┴──────────────┤
│  面包屑导航 + 状态栏                               │
└──────────────────────────────────────────────────┘
```

### 4.3 Tauri 多窗口

所有面板可分离（detachable）：
- 文件树、属性面板、标签页均可拖出成独立窗口
- 通过 Tauri WebviewWindow API 实现
- 跨窗口通信通过 Tauri 事件系统 + 共享 Zustand store

## 7. 与 2026-07-01 原版设计的关键差异

| 维度 | 原版 v1 | v2 |
|------|---------|-----|
| 架构视图 | 无，直接进入文件 | 架构页面（关系图谱）为首页 |
| 页面结构 | 双层画布统一 | 架构页 + 设计页 两大页面 |
| 节点组织 | signal/computed/fn/view 平铺 | 代码画布只负责 fn 逻辑流，signal/prop/event 在面板管理 |
| 节点类型 | 按语义分类（view-element, branch, for-each...） | 函数头 / 骨架节点 / 代码块节点 / return 节点 |
| 架构模式 | 无 | 整体架构 + 局部架构 两级体系 |
| 左侧面板 | 多个面板 | 仅组件面板 + 组件树面板 |
| 数据文件 | 仅 .omni 源码 | .omni（PID 注释）+ 项目根 JSON |
| fn 命名 | fn 节点 | 自定义函数（fn）+ 代码块节点（fn 内部代码） |
| 界面预览 | 单组件预览 | 架构页=应用完整渲染，设计页=当前组件预览 |

## 8. 待定 & 后期扩展

### 8.1 动画编辑器（后期扩展）
- Motion 和 Timeline 在架构图谱中作为特殊节点类型显示
- 具体时间轴轨道编辑为后期功能

### 8.2 样式编辑器（后期扩展）
- CSS 属性面板增强（调色板、数值滑块、渐变编辑器）
- 设计 Token 系统（shared/theme.omni）

### 8.3 AI 辅助架构
- Poiesis 分析图谱，主动建议架构优化
- "你有两个组件都直接依赖了同一个 Store signal，建议提取共享 computed"
- 自动检测循环依赖、层级违规

### 8.4 Import 管理（全自动）
- 拖入组件到画布 → 自动添加 import
- 删除最后引用 → 自动移除 import
- Monaco 手动编辑 import 同样被识别和保留
