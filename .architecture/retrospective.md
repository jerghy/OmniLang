# OmniLang 工作区架构回溯

> 2026-07-27 | 覆盖：编译器管线 · 编辑器演进 · 目标精简 · Deferred JS · 设计迁移

## 1. 编译器管线设计

**决策**：经典的 Lexer → Parser → Semantic → IR → Codegen 五阶段管线。

**当时背景**：OmniLang 需要同时输出 OmniView（HTML/JS/CSS）、React、Flutter 等多种目标。直接在 AST 上做代码生成会导致每个目标都重新实现一遍语义分析。

**为什么这样选**：IR（中间表示）层作为"真理之源"——语义分析只做一次，所有目标后端从同一份 IR 产出代码。这避免了 N×M 的复杂度爆炸（N 个分析阶段 × M 个目标）。

**结果**：9 个代码生成目标全部从 IR 输出，新增语言特性只需在 lowering 阶段实现一次。IR 设计经受住了考验——2026 年 7 月添加源映射管线时，只需修改 lowering 和 writer 层。

**学到什么**：IR 的类型系统设计（TypeKind/TypeIR）应该更早考虑递归泛型——当前 TypeKind::Named 存储不透明字符串，类型验证留到 codegen 阶段，增加了后端复杂度。P24 已在修复。

## 2. 编辑器范式演进：CodeCard → Blockly → SVG → Monaco

**决策**：经过 4 次范式转换，最终选择 Monaco Editor（VS Code 内核）作为文本编辑基础。

**当时背景**：
- v3 CodeCard（扁平积木）：光标方案失败 4 次，积木拖拽的 UX 达不到预期
- v4 Blockly-style：可视化编程积木，但复杂逻辑（表达式、闭包）用积木表达极不自然
- SVG 投影：尝试在画布上用 SVG 渲染代码结构，性能瓶颈严重

**为什么选 Monaco**：文本编辑是程序员最熟悉的交互范式。Monaco 提供成熟的语法高亮、自动补全、错误标记等基础设施。结构投影（structural projection）的长期愿景保留，但当前阶段文本编辑 + WASM 语义分析是务实选择。

**结果**：编辑器从零实现了 OmniLang 语法高亮、PID 注解解析、WASM 增量编译（0.31s/20 文件）。[[poiesis-codeblock-editor-v5]]

**学到什么**：可视化编程的 UX 挑战被严重低估。文本编辑的"自由度"（随时输入任何字符）是可视化积木难以替代的。结构投影方案 3（Monaco + AST 感知，见 [[poiesis-structural-projection-editor]]）是最可行的长期方向。

## 3. 9→3 代码生成目标精简

**决策**：2026-07-26，从 9 个默认编译目标缩减为 3 个 P0 目标（OmniView + React + Flutter），其余 6 个转为 feature-gated。

**当时背景**：9 个后端中仅 OmniView 在编辑器中有实际用户。每次 IR 变更需要接触 6+ 代码生成后端。9 个几乎完全相同的回归测试文件（每个 58 行）增加维护噪音。架构评审中 5/11 专家独立识别此问题。

**为什么现在做**：P15 的实施暴露了 115 个预存编译错误（HashMap→FxHashMap 迁移未传播到 feature-gated 后端测试文件），证明"可编译但不维护"的策略已经失败了——这些代码在无人知晓的情况下腐烂。

**结果**：P0 三个后端有参数化回归测试（P19），其余保留在 feature flag 后可编译。预估节省每个 IR 变更 30-50% 的机械性同步工作。

**学到什么**：YAGNI 原则对代码生成目标完全适用。如果没有活跃用户，feature-gated 不等于"维护"——代码会在无人注意的情况下位腐化（bitrot）。

## 4. Deferred JS 交换机制

**决策**：OmniView 运行时使用 Deferred JS 模式——编译时生成静态 HTML/CSS，运行时通过 `data-nid` 属性和信号系统做最小化 DOM 更新。

**当时背景**：传统的 SPA 框架（React/Vue）在客户端做完整的虚拟 DOM diff，OmniView 的目标是"接近静态 HTML 的性能，但保留响应式能力"。

**为什么这样设计**：
- 编译时确定所有 DOM 结构（`data-nid` 标记每个节点）
- 运行时仅更新信号绑定的具体节点（`textContent`、`className` 等）
- 不维护虚拟 DOM 树——直接操作真实 DOM

**结果**：OmniView 产出的 HTML 是有效的静态页面（SEO 友好），JS 运行时 (~5KB gzipped) 仅处理响应式绑定。源映射系统（`data-nid` + `__omni_reportError`）提供运行时错误定位。

**学到什么**：编译时优化 + 运行时最小化的模式在 UI 框架中是可行的第三条路（区别于纯静态和纯 SPA）。关键挑战是 motion/animation 子系统——它需要命令式时间线控制，与声明式模板存在阻抗。

## 5. indigo → terracotta 设计迁移

**决策**：2026-07-24，将 Poiesis 编辑器的设计 Token 体系从 indigo 色系迁移到 terracotta（陶土色）色系。

**当时背景**：原始 indigo 色系是快速原型阶段的占位选择，缺乏系统的设计意图。编辑器需要更有"工具感"的视觉方向，区别于消费级应用的蓝紫色系。

**为什么 terracotta**：暖色调（橙棕系）在深色模式下提供更好的对比度和"专业工具"的氛围，与代码编辑器的使用场景（长时间专注工作）更匹配。

**结果**：完整的 Token 体系迁移——11 项决策记录、CSS 变量重命名、组件逐个更新。[[poiesis-design-migration-2026-07-24]]

**学到什么**：设计 Token 体系应该在项目初期就建立命名约定（而不是"先用着再改"）。色彩空间的系统性（OKLCH）比具体色值更重要——迁移到 OKLCH 后，主题切换（明/暗）的自动适配变得可行。

## 关键架构原则（通过以上决策浮现）

1. **务实优先**：文本编辑 > 可视化积木，3 目标 > 9 目标，先用起来再优化
2. **编译时 > 运行时**：把复杂度推到编译阶段（IR lowering、CSS 变量解析、Deferred JS）
3. **类型安全是投资而非成本**：FxHashMap/TypeKind 等类型改进在短期内增加工作量，但防止了位腐化
4. **测试保护先行**：参数化测试框架（P19）必须在类型重构（P24）之前——这是 plan-review 的关键修正
