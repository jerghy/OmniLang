# ADR-044: Theme Store Mode ↔ __omni_theme Auto-Sync

## Status

Accepted

## Context

The OmniView theme system has two independent mechanisms for theme management:

1. **`__omni_theme` runtime** — generated by `emit_theme_runtime()` from design blocks that declare `@themes`. Manages the `data-theme` attribute on `<html>` via `set()`, `toggle()`, `init()` methods, with `localStorage` persistence and `prefers-color-scheme` auto-detection. This is what actually switches CSS variables for dark/light mode.

2. **ThemeStore signals** — user-declared store with a `mode: String` signal (values "light"/"dark"), getters (`modeLabel`, `nextLabel`), and actions (`toggle()`, `setMode()`), generated by `emit_store()`.

These two mechanisms were completely disconnected. When `ThemeStore.toggle()` called `mode = "dark"`, it only set the reactive signal via `__omni_subs.get("ThemeStore_mode").set("dark")`, but did NOT call `__omni_theme.set("dark")`. This meant the UI text updated ("Dark Mode") but the CSS variables never switched because `data-theme` on `<html>` remained "light".

The bug was discovered during E2E testing of the learn-omniview project's Settings page. While the mode indicator and toggle count updated correctly, `document.documentElement.dataset.theme` remained unchanged, making the theme switching purely cosmetic — the actual CSS theme variables never toggled.

## Decision Drivers

- Theme switching must actually work (not just update UI text but also switch CSS variables)
- Fix must be in the compiler codegen, not in Omni source files (it's a compiler bug, not a user error)
- Must handle initial load correctly: respect `localStorage`-saved theme and `prefers-color-scheme`
- Zero runtime overhead when no theme store exists or no design block declares `@themes`
- Must be robust — any store with a "mode" signal should sync, not just stores named "ThemeStore"

## Decision

Add auto-sync logic in the OmniView codegen that bridges store "mode" signals to the `__omni_theme` runtime.

### Mechanism

In `omnilang/src/codegen/omniview/mod.rs`, after `emit_theme_runtime()` and before `emit_dom_and_bindings()`:

1. Check if any design block declares `@themes` (i.e., `__omni_theme` will be emitted)
2. If yes, iterate all stores and find those with a `"mode"` signal
3. For each, emit `mount_js` code that:
   - **Init**: Sets the store mode signal to match `__omni_theme.current` (so the store picks up `localStorage`/`prefers-color-scheme`)
   - **Reactive**: Creates a `__omni_effect` that calls `__omni_theme.set(modeSignal.value)` whenever the signal changes

### Generated Code Pattern

```js
// ── Theme mode sync: ThemeStore_mode ↔ __omni_theme ──
(function() {
  // 1. Init: respect saved/preferred theme from __omni_theme.init()
  if (ThemeStore_mode.value !== __omni_theme.current) {
    __omni_subs.get("ThemeStore_mode").set(__omni_theme.current);
  }
  // 2. Reactive: store mode changes propagate to __omni_theme
  __omni_effect(function () { __omni_theme.set(ThemeStore_mode.value); });
})();
```

### Why mount_js

`mount_js` is emitted after both `emit_store()` and `emit_theme_runtime()` in the JS output order. This guarantees `__omni_theme` exists when the sync code runs.

### Architectural Components Affected

* `omnilang/src/codegen/omniview/mod.rs` — codegen main generation function (single file, <30 lines added)
* `build/debug/index.js` — generated output (consumers unaffected, only gains new behavior)

### Interface Changes

* No public API changes. Store actions (`toggle()`, `setMode()`) continue to work identically.
* The `mount_js` output now includes a new `__omni_effect` for theme sync when applicable.

## Consequences

### Positive

* **Theme switching now fully works**: Changing the store mode signal automatically updates `data-theme` on `<html>`, which triggers CSS variable switches.
* **Zero user-code changes**: No modifications needed to `.omni` source files. All existing ThemeStore usages immediately gain the correct behavior.
* **Robust signal tracking**: The `__omni_effect` reacts to ANY change to the mode signal, regardless of which action or direct assignment triggered it.
* **Initial load respects saved preference**: On first page load, if `localStorage` has a saved dark theme or `prefers-color-scheme: dark` is active, the store mode is initialized from `__omni_theme.current` rather than the hardcoded default.
* **Framework-agnostic detection**: Any store with a "mode" signal is auto-synced, not just stores named "ThemeStore".

### Negative

* **Additional mount_js code**: For projects with both a design block (themes) and a store with "mode" signal, a small IIFE (~7 lines) is added to the mount lifecycle.
* **Implicit coupling**: The sync is implicit — users don't explicitly wire the store to the theme system. However, this is considered appropriate because:
  - The coupling is unidirectional (mode → `__omni_theme`)
  - It follows the principle of least surprise (changing mode should switch the theme)
  - ADR-042/043 follow the same principle of implicit codegen-level integration

### Neutral

* **Naming convention dependency**: The detection relies on the signal being named "mode". This was already the de facto convention in the codebase (ThemeStore, the only store with theme switching, uses this name).
* **Requires both a design block with @themes and a store with "mode"**: If only one exists, no sync code is emitted.

## Implementation Strategy

### Blast Radius

**Impact Scope**: Single file change in the OmniView codegen. Only affects the generated JS output.

**Affected Components**:
- `omnilang/src/codegen/omniview/mod.rs` — the only file modified
- Generated `index.js` — the output gains a mount_js IIFE when conditions are met

**User Impact**: Positive — theme switching now works. Zero behavioral change for projects without themes or without a mode-signal store.

**Risk Mitigation**:
- Guard condition (`has_themes`) ensures sync code is only emitted when `__omni_theme` actually exists
- No new public API or configuration surface introduced
- All existing tests pass (263 omnilang + 530 omnilang-core)

### Reversibility

**Reversibility Level**: High

**Rollback Feasibility**: Simply revert the single-file change or regenerate without the condition.

### Sequencing & Timing

**Prerequisites**:
- One existing design block with `@themes` decoration (already implemented in learn-omniview's `design.omni`)
- One existing store with a "mode" signal (already implemented in `ThemeStore.omni`)

**Sequencing Concerns**: None — single-file change with no cross-dependency.

**Readiness Assessment**: Ready to implement (already implemented and verified).

### Social Cost

**Learning Curve**: Low
- The change is in the compiler codegen, invisible to component authors
- Developers continue to use `ThemeStore.toggle()` or `mode = "dark"` as before

**Cognitive Load**: Near zero — this bridges an architectural gap that previously caused confusion (theme toggle appeared to work but didn't actually switch CSS variables).

### Confidence Assessment

**Model Correctness Confidence**: High
- The `__omni_effect` wraps the signal reference, so it fires on any change
- Two-way init handles the edge case of saved/preferred theme vs. store default
- Verified via browser MCP testing with `document.documentElement.dataset.theme` evaluation

**Assumptions**:
1. Signal named "mode" with string values "light"/"dark" is the theme pattern — **Validation**: Confirmed by existing ThemeStore.omni usage.

**Edge Cases**:
- Multiple stores with "mode" signals: each gets its own sync IIFE — all will sync, but last write wins in `__omni_theme.set()`. This is acceptable; having two theme stores is already an architectural smell.
- Store initialized with "dark" but `__omni_theme.current` is "light": the init sync overrides the store to match `__omni_theme`, which respects saved/preferred theme. This is the correct behavior.

## Alternatives Considered

### Alternative 1: Manual action-level codegen in ThemeStore.toggle()

Add `__omni_theme.set(mode)` inside the generated `ThemeStore_toggle()` function.

**Pros:**
- Explicit coupling visible in generated code
- No reactive effect overhead

**Cons:**
- Only catches `toggle()`, not `setMode()` or future actions
- Would need to be added for every action that changes mode
- Fragile — easy to forget when adding new theme stores

### Alternative 2: Runtime theme watcher (JS-level)

Add global JS in `emit_theme_runtime()` that watches ALL signal changes and auto-syncs those matching a pattern.

**Pros:**
- Would work without codegen changes to stores
- Framework-level solution

**Cons:**
- Expensive — requires watching all signals at runtime
- Magic behavior hard to understand
- Would need new runtime API (`__omni_watch()`)

### Alternative 3: Developer-explicit wiring in .omni source

Add Omni language syntax for `@theme mode` or similar directive in the store or component to explicitly sync.

**Pros:**
- Explicit, no magic
- Language-level semantic clarity

**Cons:**
- Requires new Omni syntax
- Every theme store author must add the directive
- User-facing complexity for what should be automatic behavior

## Pragmatic Enforcer Analysis

**Reviewer**: Pragmatic Enforcer
**Mode**: Balanced

**Overall Decision Complexity Assessment**: Low complexity, high necessity. The fix is a targeted 30-line addition in a single file that closes an architectural gap between two independent mechanisms that were clearly designed to work together but were never wired up.

**Decision Challenge**:

**Necessity Assessment**: 9/10
- **Current need**: Theme switching is completely broken without this — UI updates but CSS doesn't switch. This is a P0 bug.
- **Future need**: Any project with themes + theme store requires this wiring.
- **Cost of waiting**: Every project with themes produces broken theme switching.
- **Evidence of need**: Verified via browser MCP — `document.documentElement.dataset.theme` remained "light" after clicking the Dark toggle.

**Complexity Assessment**: 2/10
- **Added complexity**: ~30 lines in a single codegen file. No new types, no new runtime code.
- **Maintenance burden**: Near zero — the pattern is declarative (emit an IIFE that does one thing).
- **Dependencies introduced**: None. The `__omni_effect` and `__omni_theme.set()` are both existing APIs.

**Alternative Analysis**:
- The three alternatives listed above were considered. All are either more complex (Alternative 2), more fragile (Alternative 1), or impose user-facing cost with no benefit (Alternative 3).
- The chosen approach — reactive `__omni_effect` in generated mount code — is the simplest possible solution that handles all cases.

**Simpler Alternative Proposal**: None. This IS the simplest alternative. A "do nothing" option would leave theme switching broken.

**Recommendation**: ✅ Approve decision

**Pragmatic Score**:
- **Necessity**: 9/10
- **Complexity**: 2/10
- **Ratio**: 0.22 *(Target: <1.5 for balanced mode)*

**Overall Assessment**: Appropriate engineering. Fixes a concrete P0 bug with minimal complexity. The auto-sync via reactive effect is the right approach because it catches any store mode change regardless of which action produced it.
