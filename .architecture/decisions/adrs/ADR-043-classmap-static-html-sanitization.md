# ADR-043: ClassMap Static HTML Sanitization and Scroll Trigger Defense

## Status

Accepted

## Context

Browser MCP end-to-end testing of the learn-omniview project (66+ source files across 10 pages) revealed two codegen defects:

### Defect 1: ClassMap Static HTML Over-inclusion

The `class: { ... }` syntax (ClassMap) in Omni view templates allows both static boolean literals and dynamic expressions as class conditions. The IR lowerer in `crates/omnilang-core/src/ir/lower/view.rs` was including ALL non-false entries in the static HTML `class` attribute, including names whose condition depends on runtime function calls (e.g., `isActive("home")`).

**Example**: TabBar buttons use `class: { tab: true, tabActive: isActive("home") }`. The lowerer correctly extracted `tabActive` as a dynamic binding (with a corresponding `classList.toggle` runtime effect), but also incorrectly included `"tabActive"` in the static HTML class string for ALL 10 tab buttons. The runtime effect corrected this after JS execution, but the initial render showed all tabs as active.

**Root cause**: `lower/view.rs` line 382-384 had the logic `if !skip { static_classes.push(key.clone()); }` — only `Bool(false)` was skipped. Dynamic expressions (function calls, signal reads, etc.) passed through into the static HTML as if they were truthy constants.

### Defect 2: Scroll Trigger `__omni_scrollElements` Guard

The `__omni_scrollRemoveEntry` function in the scroll trigger runtime codegen (`motion_triggers.rs`) checked `if (!el) return;` but did not check for `__omni_scrollElements` being null/undefined. While the initial element check prevents crashes in the common case, the `__omni_scrollElements.filter(...)` call on line 157 would throw if `__omni_scrollElements` were somehow null — a defensive programming gap exposed during review.

## Decision Drivers

- Static HTML should only contain classes guaranteed to be present at runtime
- All dynamic class bindings should be exclusively managed by runtime `classList.toggle` effects
- Runtime code should be defensive against null/undefined state arrays
- Zero regression impact: all 263 existing tests must pass after changes

## Decision

### D1: Exclude Dynamic Expressions from Static HTML Class String

Change the ClassMap lowering logic to only include `Bool(true)` literals in the static HTML class string. Dynamic expressions (function calls, signal reads, computed properties) are excluded from the static HTML and left entirely to the runtime `classList.toggle` effects generated by `emit_class_map_effects()`.

**Before** (lower/view.rs):
```rust
if !skip {  // skips only Bool(false)
    static_classes.push(key.clone());
}
```

**After**:
```rust
if let Expr::Literal(Literal::Bool(true), _) = val_expr {
    static_classes.push(key.clone());
}
```

### D2: Add `__omni_scrollElements` Null Guard

The `__omni_scrollRemoveEntry` guard is updated from `if (!el) return;` to `if (!el || !__omni_scrollElements) return;` to prevent crashes if the scroll elements array is uninitialized.

**Architectural Components Affected:**
- `crates/omnilang-core/src/ir/lower/view.rs` — ClassMap lowering (D1)
- `omnilang/src/codegen/omniview/motion_triggers.rs` — Scroll trigger codegen (D2, already had the fix in source, snapshot lagged)
- `omnilang/src/codegen/omniview/tests_regression/snapshots/.../scroll_trigger.snap` — Snapshot sync (D2)

**Interface Changes:**
- None — both changes are internal codegen refinements with zero public API impact

## Consequences

### Positive

- Static HTML is semantically correct: only statically-known classes appear in the initial markup
- Eliminates visual flash where dynamic classes briefly show on wrong elements before JS hydrates
- Runtime effects continue to manage all dynamic classes identically — no behavior change after JS execution
- Defensive null guard prevents a potential TypeError in scroll cleanup path
- All 263 library tests pass with zero regression

### Negative

- Minimal: Initial page render may briefly lack a dynamic class (e.g., `tabActive` on the home tab) before JS executes — visually indistinguishable from the previous "all tabs active" flash, and strictly less wrong

### Neutral

- The runtime `classList.toggle` effects already existed and are unchanged — D1 only removes the incorrect static HTML inclusion
- D2 was already in the codegen source but the snapshot test hadn't been updated

## Implementation Strategy

### Blast Radius

**Impact Scope**: Small — ClassMap lowering logic (one condition change) and scroll trigger guard (one `||` addition). Both are in core codegen paths but the change is purely additive/restrictive.

**Affected Components**:
- `lower/view.rs` — ClassMap static class string construction
- `motion_triggers.rs` — Scroll element guard (codegen already correct)
- Scroll trigger snapshot — Test sync only

**Risk Mitigation**:
- The ClassMap change makes the static HTML more conservative (fewer classes), so the worst case is a missing initial class that the runtime effect immediately adds — no visual regression from the corrected state
- Test suite covers ClassMap bindings via regression tests — all pass

### Reversibility

**Reversibility Level**: High

**Rollback Feasibility**: Single-line change in lower/view.rs — revert `if let ... = val_expr` back to `if !skip`. Snapshot revert via `git checkout`.

### Sequencing & Timing

**Prerequisites**: None — fix was applied directly during E2E test session.

**System Readiness**: Ready — changes compiled, built, and verified end-to-end with Browser MCP.

## Alternatives Considered

### Alternative 1: Evaluate Function Calls at Compile Time

Attempt to evaluate `isActive("home")` at compile time by constant-folding function calls with known arguments.

**Pros:**
- Perfect static HTML — only the truly active button gets `tabActive`
- Eliminates any brief flash

**Cons:**
- Requires implementing a constant-folding evaluator for the function call subset of the IR
- Not possible in general — many functions have side effects or depend on external state
- **Massive** complexity for a cosmetic issue
- **Rejected**: YAGNI violation — runtime effects already handle this correctly

### Alternative 2: Wait for JS to Apply All Classes Before Render

Render the entire component tree in JS and block the initial paint until effects resolve.

**Pros:**
- No flash at all

**Cons:**
- Requires async hydration infrastructure
- Opposed to the debug mode design philosophy of server-rendered HTML for SEO
- **Rejected**: Fundamental architecture change far beyond the scope of the bug

### Alternative 3: Two-Pass Codegen (Current Approach + Accept)

Keep current approach (include all dynamic classes in static HTML) and accept the brief flash of incorrect state.

**Cons:**
- Initial HTML is semantically incorrect — shows all tabs as active
- Accessibility tree may report incorrect state before JS hydration
- **Rejected**: The fix (D1) is a one-line condition change with zero negative consequences
